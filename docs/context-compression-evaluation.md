# CLI 대화 이력 관리: 평가와 개선 (2026-09-28)

## 요약

CLI는 매 턴 최근 6,000자만 남기고 오래된 대화를 버리고 있었다. 대화 압축 코드(`compress.ts`)는 작성만 되어 있고 호출되지 않았다. 긴 대화에서 앞쪽 정보를 기억하는지 측정해 보니, 대화 중 나온 사실 30개 중 **3개(10%)**만 답했다.

압축을 로컬 모델의 컨텍스트 한도에 맞게 다시 설계하고 CLI에 연결한 뒤, 같은 평가에서 **19개(63%)**를 답했다. 질문 한 번에 들어가는 입력은 자르지 않은 대화의 약 22%(17,800 → 4,000토큰)다.

## 발견한 문제

| 문제 | 근거 |
|---|---|
| 최근 6,000자만 남기고 나머지를 버림 (`truncateHistory(messages, 6000)`) | 한국어 기준 약 2,700토큰으로, 16K 컨텍스트의 17%만 사용. 대화 앞쪽 사실 12개 중 0개 기억 |
| 압축 코드가 CLI에 연결되지 않음 | `compressHistory`를 호출하는 곳이 없음 |
| 압축 기준이 10만 자 | 약 45,000토큰으로 16K 한도의 약 3배. 기준에 닿기 전에 모델 서버가 앞부분을 잘라냄 |
| 모델 서버는 한도를 넘는 입력을 에러 없이 잘라냄 | Ollama에서 약 9만 자 입력의 맨 앞 정보를 두 모델 모두 찾지 못함 (`prompt_tokens`가 16,386에서 멈춤) |
| 요약 모델이 사용자의 결정 대신 문서 내용을 요약함 | 첫 설계에서 첫 조각의 사실 5개가 요약에 하나도 남지 않고, 문서 설명과 코드 예시로 채워짐 |
| 이어서 요약할 때 모델이 스냅샷을 다시 쓰며 앞 정보를 잃음 | 조각 2·3의 사실이 다음 조각 요약에서 사라짐 |

## 개선

`src/cli/hooks/useLlmStream/compress.ts`, `useLlmStream.ts`, `src/config.ts`

1. **토큰 기준:** 컨텍스트 한도(`LLM_CONTEXT_TOKENS`, 기본 16,384)의 60%를 넘으면 압축하고, 최근 20%는 원문으로 둔다. 토큰 수는 cl100k로 추정한다. 한국어 문서에서 실제 로컬 모델 토큰 수의 1.1~1.7배로 나와 넘치지 않는 쪽으로 틀린다.
2. **나눠서 처리:** 요약할 분량을 한도의 45% 조각으로 나눈다. 자르는 지점은 user 턴 경계로 한다.
3. **스냅샷 구성:**
   - 사용자 발화는 요약하지 않고 원문(최대 400자)으로 옮긴다.
   - 모델은 조각마다 구체적인 값이 있는 결정·결과만 한 줄씩 뽑는다.
   - 코드가 그 줄들을 뒤에 덧붙인다. 모델이 스냅샷 전체를 다시 쓰지 않는다.
4. **CLI 연결:** 매 턴 시작 전에 압축하고, 압축 뒤에도 넘치면 한도의 70%에 맞춰 오래된 메시지부터 버리는 안전장치를 둔다. 요약 중에는 화면에 진행 상태를 표시한다.
5. **실패 처리:** 모델 호출이 실패하거나 결과가 원본보다 크면 원본을 그대로 쓴다.

## 평가

`scripts/eval/context-memory.ts`, 세션 생성 `eval/context/make_sessions.py` (Vault 내용이 들어가므로 세션과 결과는 커밋하지 않음)

- **세션:** 16턴 대화 3개(각 3.5~4만 자, 16K 한도를 넘는 약 25,000 cl100k 토큰). 실제 Vault 문서를 긴 답변으로 쓰고, 세션마다 나중에 물어볼 사실 10개(경로, 버전, 수치, 규칙, 담당자 등)를 0~14턴에 나눠 심었다. 사용자 발화와 답변에 반씩 넣었다.
- **채점:** 대화를 조건별로 줄인 뒤 사실마다 질문하고, 답에 정답 키워드가 있으면 정답으로 본다. 질문은 temperature 0이다.
- **모델:** Ollama `exaone3.5:7.8b`, 컨텍스트 16,384.

| 조건 | 정답 (30개) | 앞쪽 0~4턴 | 뒤쪽 10~14턴 | 질문당 입력 토큰 | 요약 시간 / 호출 |
|---|---:|---:|---:|---:|---:|
| 수정 전 CLI (최근 6,000자) | 3 (10%) | 0/12 | 3/10 | 2,225 | - |
| 자르지 않음 (서버가 앞부분 절단) | 10 (33%) | 0/12 | 8/10 | 17,793 | - |
| 수정 전 압축 코드 (기준만 낮춰 실행) | 10 (33%) | 0/12 | 7/10 | 5,872 | 65초 / 2회 |
| 첫 설계 (조각마다 스냅샷 재작성) | 10 (33%) | 4/12 | 5/10 | 3,045 | 84초 / 4회 |
| **최종 설계** | **19 (63%)** | **7/12** | **8/10** | **3,988** | **61초 / 4회** |
| 최종 설계 + 조각별 보완 호출 | 18 (60%) | 7/12 | 7/10 | 4,238 | 55초 / 8회 |

짝지은 부트스트랩 95% 신뢰구간(정답률 차이):

- 수정 전 CLI → 최종: +0.53 [+0.37, +0.70]
- 자르지 않음 → 최종: +0.30 [+0.10, +0.50]
- 첫 설계 → 최종: +0.30 [+0.10, +0.50]
- 최종 → 보완 호출 추가: -0.03 [-0.10, 0.00]

보완 호출은 모델 호출을 두 배로 쓰면서 나아지지 않아 기본값에서 뺐다(`verify: false`).

## 한계와 다음 단계

- **여전히 3분의 1을 놓친다.** 최종 설계가 놓친 11개 중 9개는 스냅샷에 없었다. 대부분 긴 답변 중간에 들어 있던 결정이고, 7.8B 모델이 조각에서 사실을 뽑다가 놓친 것이다. 경로·버전·수치처럼 형태가 뚜렷한 값을 규칙으로 함께 뽑는 방법을 같은 평가로 비교할 수 있다.
- **요약 결과가 실행마다 달라진다.** 요약 호출은 제품 코드 그대로 기본 temperature를 쓴다. 같은 첫 설계가 사전 점검에서는 한 세션 5/10, 본 실행에서는 3/10이었다. 수치는 1회 실행 결과다.
- **한 턴 안의 도구 결과는 다루지 않는다.** 도구 호출 루프 안에서 쌓이는 결과(최대 10회 × 8,000자)는 이 압축이 다루지 않는다.
- **세션은 합성이다.** 실제 CLI 사용 기록이 아니라 Vault 문서로 만든 세션이다.
