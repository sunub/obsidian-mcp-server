Q1. "dense 검색이 없으면 RAG라고 할 수 없나요?"

🎤 30초 답변
아닙니다. RAG는 "외부 지식을 검색해서 생성 모델의 입력에 넣는다"는 구조를 가리키고, 검색 방식은 정해져 있지 않습니다. RAG라는 이름을 만든 Lewis et al.(2020) 논문은 dense retriever를 썼지만, 이후 In-Context RALM(Ram et al., 2023)은 BM25만으로도 언어 모델 성능이 크게 오른다는 것을 보였습니다. BEIR 벤치마크에서도 BM25는 여러 dense 모델보다 일반화를 잘했고, 그래서 요즘은 BM25와 dense를 같이 쓰는 하이브리드가 흔합니다. 제 프로젝트도 로컬 모델이 없으면 키워드 검색만으로 동작하고, 모델이 있으면 두 결과를 RRF로 합칩니다.

2분으로 늘릴 때 덧붙일 근거

  1. 정의의 출처. Lewis et al.은 RAG를 사전학습된 생성 모델(parametric memory)과 검색으로 접근하는 외부 지식(non-parametric memory)을 결합한 모델로 정의했다. 그 논문에서 외부 지식은 위키피디아의 dense vector index였다. 즉 dense는 원 논문의 구현 선택이지 정의의 조건이 아니다. [[P:R1]] → RAG의 구조
  2. sparse만으로도 효과가 있다. In-Context RALM은 모델 구조를 바꾸지 않고 검색한 문서를 프롬프트 앞에 붙이기만 했는데, 기성 BM25 검색기를 쓴 345M GPT-2가 762M GPT-2보다 나았다. [[P:R5]]
  3. dense가 항상 낫지는 않다. BEIR(18개 데이터셋, zero-shot)에서 BM25는 견고한 기준선이었고, dense 모델은 학습 분포 밖에서 BM25보다 크게 떨어지는 경우가 있었다. [[P:R7]] Weller et al.(ICLR 2026)은 단일 벡터 임베딩의 차원 수가 표현할 수 있는 top-k 조합을 이론적으로 제한한다는 것을 보였고, LIMIT 데이터셋에서 최신 임베딩 모델은 고전했지만 BM25는 거의 만점이었다. [[P:R8]] → Dense 검색
  4. 에이전트 시대의 흐름. Anthropic은 Claude Code가 미리 만든 인덱스 대신 glob, grep으로 필요한 순간에 파일을 찾는(just-in-time) 방식을 쓰고, 처음부터 넣는 컨텍스트와 섞는 하이브리드라고 설명한다. [[D:R20]]
  5. 내 프로젝트의 측정. 같은 질의 42개에서 키워드 검색만 쓴 구성이 Recall@5 0.665였고, 버그가 있던 당시 벡터 검색만 쓴 구성은 0.127이었다. [[E:4.1]] → 개선 이야기
⚠️ 반문 대비: "그럼 dense는 필요 없나요?"

그렇지는 않습니다. 둘은 실패하는 질의가 다릅니다. BM25는 질의와 문서가 같은 단어를 써야 찾고, dense는 표현이 달라도 의미가 비슷하면 찾지만 고유명사나 에러 코드처럼 정확히 일치해야 하는 질의에 약합니다. 제 평가셋에서도 벡터 검색의 접두사 버그를 고친 뒤 하이브리드 검색의 의미 질의 유형 MRR@10이 0.207에서 0.667로, 질의 유형 중 가장 많이 올랐습니다. [[E:4.5]] 그래서 둘 중 하나를 고르기보다 합치는 쪽을 택했습니다. → 하이브리드와 RRF

Q2. "청킹 전략은 무엇을 사용했나요?"

🎤 30초 답변
마크다운 구분자 우선의 재귀 분할(recursive character splitting)을 쓰고, 청크 길이는 임베딩 모델의 토크나이저로 세서 256토큰, 겹침 32토큰으로 자릅니다. 각 청크에는 섹션 제목과 문서 개요를 짧게 붙여 임베딩합니다. 처음에는 GPT 토크나이저 기준 500토큰이었는데, 임베딩 모델이 128토큰으로 학습됐다는 걸 확인하고 크기별로 비교 실험을 했습니다. 256으로 줄였을 때 벡터 검색 MRR@10이 0.325에서 0.456으로 유의하게 올랐고, 128은 조금 더 좋았지만 청크가 2.3배로 늘어서 256을 골랐습니다. 제목 기준 분할도 시험했는데 추가 이득이 없었습니다.

⚠️ 반문 대비: "청크가 문맥을 잃는 문제는요?"

청크 앞에 섹션 제목과 문서 개요를 붙여 일부 보완했습니다. Anthropic의 Contextual Retrieval과 같은 방향인데, 그쪽은 LLM으로 청크마다 문맥 설명을 생성하고 저는 비용 때문에 제목 구조만 씁니다. 문맥을 붙이면 임베딩 입력이 길어지므로 청크 크기를 정할 때 여유를 남겨야 했습니다. 500토큰 기준으로 자르면 문맥을 붙인 뒤 390개 청크가 입력 한도를 넘어 잘렸습니다. [[D:R16]] [[E:4.8]] → 청킹

개념 1

RAG의 구조

RAG는 특정 기술이 아니라 구조입니다. 검색(Retrieval)으로 자료를 찾아 입력을 보강(Augmented)한 뒤 생성(Generation)합니다.

🎯 학습 목표
  • RAG의 정의를 parametric / non-parametric memory로 설명한다.
  • 색인 단계와 질의 단계에 무엇이 있는지 그림 없이 말한다.
  • "검색 방식은 정의의 일부가 아니다"를 원문으로 뒷받침한다.

📖 정의: 두 종류의 기억

Lewis et al.(2020)은 모델이 쓰는 지식을 두 종류로 나눴습니다. [[P:R1]]

🧠 parametric memory

모델 가중치에 저장된 지식

👍 빠르고, 추론에 녹아 있다

👎 바꾸려면 다시 학습해야 하고, 출처를 댈 수 없고, 환각이 생긴다

📚 non-parametric memory

검색으로 꺼내는 외부 문서

👍 문서만 바꾸면 최신이 되고, 출처를 보여 줄 수 있다

👎 검색이 틀리면 답도 틀린다

RAG는 이 둘을 결합합니다. 원 논문은 외부 지식으로 위키피디아의 dense vector index를 썼지만, 그것은 구현 선택입니다. 같은 시기의 REALM은 검색기를 사전학습 단계부터 함께 학습했고, RAG는 사전학습된 검색기와 생성기를 결합해 미세조정했습니다. [[P:R2]]

📖 발전 단계

Gao et al.의 서베이는 RAG를 세 단계로 나눕니다. [[P:R3]] 2025년 이후에는 에이전트가 언제, 무엇을, 몇 번 검색할지 스스로 정하는 Agentic RAG가 별도 분야로 정리됐습니다. [[P:R4]]

단계특징예
Naive RAG색인 → 검색 → 생성의 고정된 한 번 흐름top-k 청크를 그대로 붙임
Advanced RAG검색 전후 최적화질의 재작성, 하이브리드 검색, 리랭킹, 압축 ← 이 프로젝트
Modular RAG모듈을 바꾸고 조합라우팅, 반복 검색, 메모리
Agentic RAG에이전트가 검색 시점과 횟수를 정함도구 호출로 검색, grep도 검색

📖 RAG가 해결하지 못하는 것

  • 검색이 틀리면 생성도 틀린다. 그래서 이 프로젝트는 생성 품질보다 검색 품질(Recall, MRR)을 먼저 측정했다.
  • 찾아도 모델이 안 쓸 수 있다. 긴 입력의 중간에 있는 정보를 덜 활용한다는 "Lost in the Middle" 결과가 있다. [[P:R18]] → 많이 넣기보다 정확한 몇 개를 넣는다.
  • 긴 컨텍스트 모델이면 RAG가 필요 없나? 4K 컨텍스트 + 검색이 16K 컨텍스트 모델과 비슷했고, 긴 컨텍스트 모델에도 검색을 더하면 더 좋아졌다는 결과가 있다. [[P:R19]]

논문이 정의한 것은 "검색으로 접근하는 외부 지식(non-parametric memory)과 생성 모델의 결합"이라는 구조이고, dense index는 그 구현이다. In-Context RALM은 BM25로 같은 구조의 효과를 보였다.
미니 RAG 실습에서 검색이 아무것도 찾지 못하면 프롬프트는 어떻게 되고, 그 결과 무엇이 문제인가?
자료 없이 질문만 들어가므로 모델은 가중치 속 지식만으로 답한다. RAG의 이점(최신성, 출처, 환각 감소)이 사라진다. 검색 품질을 먼저 재야 하는 이유다.

📖 한국어는 왜 더 어려운가

한국어는 단어에 조사와 어미가 붙는 교착어라서, 공백 단위(어절)로 색인하면 문서의 "검색을"과 질의의 "검색"이 다른 토큰이 됩니다. Elasticsearch는 이 문제를 Nori 같은 형태소 분석기로 풀고, 다국어 검색 연구에서도 한국어 BM25에 Nori를 씁니다. [[P:R17]] 다만 형태소 분석기별 한국어 검색 성능을 통제된 조건에서 비교한 공개 연구는 찾지 못했습니다. 직접 평가셋으로 재야 합니다. [[I]]

🛠 이 프로젝트에서는

질의 토큰마다 ① 원형 ② 앞뒤 문장부호를 뗀 형태 ③ 중간 문장부호로 나뉜 조각이 모두 들어 있는 문서, 이 셋 중 하나라도 맞으면 일치로 봅니다. 질의 토큰 하나는 문서당 한 번만 셉니다. [[C:Indexer.ts:96-130]]

  • 원형을 남긴 이유: 태그(c++)와 파일명(my-note)은 문장부호째 색인되기 때문.
  • 한 글자 조각을 뺀 이유: 처음 구현에서 질의 I/O(q11)가 나빠졌다. 이 규칙은 평가셋을 보고 넣은 것이라 새 질의로 다시 확인해야 한다.
  • 결과: 현재 동작의 Recall@5 0.752 → 0.800, MRR@10 0.650 → 0.711. 하이픈이 든 라이브러리 이름 질의 3개가 1위로 올라왔고 나빠진 질의는 없었다. 신뢰구간 하한이 0이라 유의하다고 단정할 수는 없다. [[E:4.9]]
🎤 면접에서 말하기
색인할 때와 질의할 때 같은 analyzer를 써야 한다는 원칙을 어긴 버그가 있었습니다. 본문은 문장부호에서 끊고 질의는 공백으로만 잘라서 tailwind-merge 같은 질의가 맞지 않았습니다. 질의 토큰도 같은 규칙으로 정리하도록 고친 뒤 Recall@5가 0.752에서 0.800으로 올랐습니다. 다만 42개 질의로는 유의하다고 말할 수 없어서 "나빠진 질의 없이 개선"이라고만 말합니다.

✅ 자가 점검

수정 전에 tailwind-merge 질의가 본문의 "tailwind-merge"와 맞지 않았던 이유는?
본문은 문장부호에서 잘려 "tailwind", "merge" 두 토큰으로 색인됐는데, 질의는 공백으로만 잘려 "tailwind-merge" 한 토큰으로 찾았다. 역색인에 그 토큰이 없다.
중간 조각 일치에서 한 글자 조각을 버리는 이유는?
"i", "o" 같은 한 글자 토큰은 거의 모든 문서에 있어서, 최소 일치 조건만 채우는 잡음이 된다. 실제로 질의 I/O의 순위가 나빠졌다.
원형 일치를 남겨 둔 이유는?
태그와 파일명은 문장부호를 포함한 원형 그대로 색인되기 때문이다. 원형을 버리면 c++ 태그를 찾을 수 없다.

📖 단계 1. TF와 IDF

문서 점수는 "질의 단어가 이 문서에 얼마나 중요한가"의 합입니다. 중요도는 두 가지로 정합니다.

TF (term frequency)

이 문서에 그 단어가 몇 번 나오나. 많을수록 관련이 높다.

IDF (inverse document frequency)

그 단어가 전체 문서 중 몇 개에 나오나. 드물수록 변별력이 높다. "것", "the"는 낮고 "LanceDB"는 높다.

@@F:tfidf@@

TF-IDF는 둘을 곱합니다. 여기에는 문제가 두 가지 있습니다.

  1. 단어가 100번 나온 문서가 10번 나온 문서보다 10배 관련 있지는 않다. → TF 포화(saturation)가 필요하다.

문서 3개, 평균 길이 avgdl = 10, k1 = 1.2, b = 0.75. 질의 "lancedb"는 문서 A(길이 5, tf 2)와 B(길이 15, tf 1)에만 나온다 (N = 3, n = 2).

IDF = ln(1 + (3 − 2 + 0.5) / (2 + 0.5)) = ln(1.6) = 0.470 A: 길이 보정 = 1 − 0.75 + 0.75 × 5/10 = 0.625 분수 = 2 × 2.2 / (2 + 1.2 × 0.625) = 4.4 / 2.75 = 1.600 점수 = 0.470 × 1.600 = 0.752 B: 길이 보정 = 1 − 0.75 + 0.75 × 15/10 = 1.375 분수 = 1 × 2.2 / (1 + 1.2 × 1.375) = 2.2 / 2.65 = 0.830 점수 = 0.470 × 0.830 = 0.390

A가 B의 약 1.9배입니다. tf는 2배지만 포화 때문에 분수는 1.9배에 그치고, A가 짧아서 오히려 이득을 봤습니다. k1 = 0이면 두 문서의 점수가 같아집니다. 위 실습에서 같은 계산을 숫자를 바꿔 가며 확인할 수 있습니다.

b = 0이면 어떤 일이 생기나? k1 → ∞이면?
b = 0이면 길이 보정값이 항상 1이라 문서 길이를 무시한다. k1 → ∞이면 분수가 tf / (길이 보정값)에 가까워져 포화가 사라지고 TF에 비례한다(TF-IDF에 가까워짐).

📖 IVF와 PQ

IVF (inverted file)

벡터를 k-means로 여러 파티션에 나누고, 질의와 가까운 파티션 몇 개(nprobes)만 본다. 정답이 다른 파티션에 있으면 놓친다.

PQ (product quantization)

벡터를 여러 조각으로 나눠 조각마다 코드북 번호로 압축한다. 메모리가 줄고 거리 계산이 빨라지지만 근사 오차가 생긴다. [[P:R26]]

하이브리드 검색과 RRF

BM25와 dense는 실패하는 질의가 다릅니다. 둘의 결과를 합칠 때는 점수가 아니라 순위로 합칩니다.

🎯 학습 목표
  • 점수 대신 순위로 합치는 이유 두 가지를 말한다.
  • RRF 수식과 k의 역할을 설명하고, 직접 계산한다.
  • 이 프로젝트가 일반론과 달리 리랭커를 뺀 이유를 숫자로 말한다.

📖 왜 점수가 아니라 순위인가

BM25 점수(0~수십, 상한 없음)와 코사인 유사도(−1~1)는 단위가 다릅니다. 그대로 더하면 한쪽이 지배합니다. min-max로 정규화해도 질의마다 분포가 달라 불안정합니다. RRF(Reciprocal Rank Fusion)는 점수를 버리고 순위만 씁니다. [[P:R11b]]

@@F:rrf@@
  • 여러 검색기에서 모두 상위에 있는 문서가 올라온다.
  • k가 크면 순위 간 차이가 줄어 하위 문서도 기여하고, 작으면 1위가 지배한다.
  • k = 60이 사실상 표준값이다. Elasticsearch의 rank_constant 기본값도 60이다. [[D:R15b]] (원 논문이 k를 어떻게 정했는지는 PDF 본문을 확인하지 못했다.)
  • Cormack et al.(SIGIR 2009)은 이 단순한 방법이 Condorcet 결합이나 개별 학습 순위 방법보다 낫다고 보고했다. [[P:R11b]]

  1. 임베딩 모델의 입력 한도. 이 프로젝트의 모델은 128토큰으로 학습됐다. 문서 전체를 넣을 수 없다. [[D:R14]]
  2. 검색 정밀도. 문서 하나에 주제가 여러 개면 벡터 하나가 모든 주제의 평균이 되어 어느 질의와도 애매하게 가깝다. [[I]]
  3. 생성 모델의 컨텍스트 예산. 관련 부분만 넣어야 비용이 줄고 "Lost in the Middle" 문제가 줄어든다. [[P:R18]]

반대로 너무 작게 자르면 청크 하나에 답을 이해할 문맥이 부족해지고, 청크 수가 늘어 색인 비용이 커집니다.

평가: 검색이 좋아졌다는 것을 어떻게 아나

이 프로젝트에서 가장 중요한 교훈입니다. 좋다고 알려진 부품(리랭커, 접두사)을 붙였는데 측정해 보니 검색이 나빠져 있었습니다.

  • 평가셋을 만들 때 지킨 원칙을 말한다.

📖 짝지은 부트스트랩 신뢰구간

질의 42개로 평균 MRR이 0.05 올랐다면, 그것은 진짜 개선일까요, 우연일까요? 같은 질의에 대한 두 구성의 차이를 질의 단위로 복원추출해 평균을 수천 번 다시 계산하면, 차이 평균의 분포가 생깁니다. 그 분포의 가운데 95% 구간이 0을 포함하지 않으면 "차이가 있다"고 말할 근거가 됩니다.

부트스트랩: 질의 수와 신뢰구간

[[SRC:metrics.mjs]]

질의별 MRR을 쉼표로 적습니다(A: 기존, B: 개선). 기본값은 설명용 예시 20개입니다. "질의 수 배율"을 올리면 같은 분포의 질의가 늘어난 것처럼 복제합니다.

해 볼 것 배율 ×1에서는 구간이 0을 걸칠 수 있지만, 질의가 늘면 같은 평균 차이로도 구간이 좁아져 0을 벗어납니다. "42개로는 유의하지 않았다"는 말이 무엇인지 체감해 보세요.

🛠 이 프로젝트의 평가 방법에서 배울 점

  1. 질의를 결과를 보기 전에 작성했다. 결과를 보고 질의를 고치면 평가셋이 현재 구현에 맞춰진다. (토큰화 수정의 한 글자 규칙은 이 원칙의 예외였고, 그래서 문서에 밝혔다.)
  2. 유형을 섞었다. 제목, 키워드, 의미, 다중 문서, 링크, 답 없음. 유형별로 봐야 "의미 질의는 나빠졌다" 같은 것이 보인다.
  3. 짝지은 부트스트랩 95% 신뢰구간을 냈다. 질의 42개는 작아서 차이가 커 보여도 유의하지 않은 경우가 많았다. "유의하지 않았다"를 숨기지 않고 말하는 것이 신뢰를 준다.
  4. 재현 코드가 실제 경로와 같은 결과를 내는지 확인했다. 42개 질의 모두 순위까지 일치.
  5. 한계: 한 사람이 만든 평가셋이라 정답 목록에 빠진 문서가 있을 수 있다. 그래서 절대값보다 구성 간 비교를 더 믿는다.

문서 단위 이진 정답이라 Recall@k와 MRR@k를 주 지표로 썼다. 청크 단위로 채점하지 않은 이유는 청킹 방식이 바뀔 때마다 정답이 무너지기 때문이다. [[E:2.1]]

③ 원인 2: 리랭커키워드로만 찾은 문서는 청크가 없어 리랭커가 본문 대신 요약·경로를 채점. 입력을 고쳐도 리랭커 없는 구성보다 MRR이 높지 않음리랭커 제거
④ 수정 후 실제 경로Recall@5 0.516 → 0.752, MRR@10 0.381 → 0.672, warm p50 5.9초 → 16ms, cold 5.8초 → 605ms. 모두 95% CI가 0을 포함하지 않음
⑤ 청킹 정제base64 이미지 제거청크 −40%, 첫 색인 −42%, 품질 유지
⑥ 청크 크기임베딩 모델 토크나이저 기준 256/32벡터만 MRR@10 0.325 → 0.456 (유의)
⑦ 질의 토큰화본문 색인과 질의의 토큰화 규칙을 맞춤Recall@5 0.752 → 0.800, MRR@10 0.650 → 0.711. 나빠진 질의 0개 (CI 하한 0이라 유의하다고 단정할 수 없음)
💡 교훈

"좋다고 알려진 부품을 붙이는 것"과 "검색이 좋아지는 것"은 다르다. 리랭커와 접두사는 둘 다 일반적으로 권장되는 기법이었지만 이 환경에서는 품질을 떨어뜨렸다. 측정하지 않으면 개선인지 악화인지 알 수 없다.

🎤 1분 버전
하이브리드 검색과 리랭커를 붙여 놓고 속도만 재고 있었는데, 정답을 찾는지는 잰 적이 없었습니다. 실제 노트로 질의 42개짜리 평가셋을 만들어 보니 현재 구성이 키워드 검색만 쓸 때보다 나빴습니다. 원인은 모델에 맞지 않는 질의 접두사와, 문서 단위 결과를 제대로 채점하지 못하던 리랭커였습니다. 둘을 고치고 리랭커를 빼자 Recall@5가 0.516에서 0.752로, MRR이 0.381에서 0.672로 오르고 지연은 6초에서 16ms로 줄었습니다. 이후 청크 크기를 임베딩 모델 기준으로 다시 정해 벡터 검색 MRR을 0.325에서 0.456으로 올렸습니다.

인용해도 되는 수치와 안 되는 수치

RAG 정의 줄기

RAG란?
검색한 외부 지식을 생성 모델 입력에 보강하는 구조. parametric + non-parametric memory. → RAG의 구조
dense 없이도 RAG인가?
예. → 두 면접 질문의 답
그럼 왜 dense를 쓰나?
vocabulary mismatch. 표현이 다른 질의를 찾는다. 내 평가에서는 벡터 검색 버그를 고친 뒤 의미 질의 MRR이 가장 크게 올랐다.
BM25와 dense가 각각 실패하는 예는?
BM25: "차량 정비"로 "자동차 수리" 문서 찾기. dense: 에러 코드, 라이브러리 이름, LIMIT 같은 조합 질의. → 의미 공간 실습
둘을 어떻게 합쳤나? k는 무엇을 조절하나?
RRF, k = 60. 점수 단위가 달라 순위로 합친다. k는 상위 순위의 지배력: 작으면 1위 중심, 크면 평평. → RRF 실습

BM25 줄기

BM25를 설명해 보세요.
IDF × TF 포화 함수, 문서 길이 정규화. k1은 포화 속도, b는 길이 정규화 강도. Lucene 기본 1.2/0.75.
TF-IDF와 차이는?
TF 포화와 문서 길이 정규화.
당신 구현은 BM25인가?
아니다. IDF 가중 불리언 매칭, k1 = 0인 BM25와 같은 구조.
그런데 왜 잘 됐나?
개인 노트는 짧고 제목·태그·고유명사 질의가 많아 TF의 이득이 작다(해석).
한국어 BM25의 문제는?
교착어. 어절 단위 색인은 조사 때문에 일치 실패. 형태소 분석(Nori 등)이나 n-gram. 색인과 질의에 같은 분석기.
SPLADE는?
모델이 단어 가중치와 확장어를 학습한 sparse 벡터. 역색인 그대로 의미 확장.

청킹 줄기

크기를 어떻게 정했나?
임베딩 모델 토크나이저 기준, 128/256/500 비교, 3회 색인 평균, 부트스트랩 CI.
왜 토크나이저가 중요한가?
같은 "500토큰"도 cl100k와 모델 토크나이저에서 길이가 다르다(중앙값 296). 한국어에서 차이가 크다.
문맥 손실은?
섹션/개요 보강. Contextual Retrieval, late chunking과의 차이를 설명.
청크 단위 vs 문서 단위 검색은?
벡터는 청크로 찾고 문서로 합친다. 키워드는 문서 단위. 단위 불일치가 리랭커 실패의 원인이었다.

평가·운영 줄기

검색 품질을 어떻게 쟀나?
42개 질의, 6개 유형, Recall@k, MRR, 짝지은 부트스트랩 CI.
리랭커를 왜 뺐나?
어떤 구성으로도 MRR을 올리지 못했고 지연은 100배 이상. 품질 차이는 유의하지 않아 "같거나 나은 품질, 훨씬 적은 비용".
생성 품질은?
아직 안 쟀다. faithfulness를 다음 단계로.
긴 컨텍스트 모델이면 RAG가 필요 없지 않나?
비용·지연, Lost in the Middle, 둘을 같이 쓸 때 가장 좋다는 연구(R18, R19).
에이전트가 grep으로 찾으면 되지 않나?
그것도 검색이다(just-in-time retrieval). 정확 일치에 강하지만 탐색이 느리고 의미 검색이 안 된다. 미리 만든 색인과 섞는 하이브리드가 실무 방향(R20).

과제 1. BM25에 필드 가중치 넣기 (제목 ×2)
buildIndex가 { id, title, text }를 받아, 제목 토큰의 tf를 2배로 세게 바꾼다. 제목에만 있는 단어로 검색했을 때 순위가 오르는지 테스트한다. 더 나아가 Robertson & Zaragoza의 BM25F와 무엇이 다른지 찾아본다(R6).
과제 2. 한국어 조사 떼기
tokenize.mjs에 간단한 조사 목록(을/를/이/가/은/는/에서/으로/로/의/와/과/도)을 떼는 함수를 넣고, 색인과 질의 양쪽에 같은 함수를 적용한다. "검색" 질의가 "검색을" 문서를 찾는지 확인하고, "고양이"가 "고양"이 되는 오분리도 관찰한다. 형태소 분석기가 왜 필요한지 체감하는 과제.
과제 3. 가중 RRF 실험
rrf(lists, 60, [1, 0.5])처럼 가중치를 바꿔 결과가 어떻게 달라지는지 표로 만든다. 가중치를 평가셋 없이 정하면 왜 위험한지 한 문장으로 쓴다.
과제 4. 내 노트로 청크 크기별 통계
노트 파일 하나를 읽어 recursiveChunks를 크기 100/200/400으로 돌리고 청크 수, 평균 길이, 50자 미만 청크 수를 출력한다. headingChunks와 비교한다.
과제 5. 작은 평가 루프 만들기
노트 8개와 질의 5개(정답 문서 지정)를 만든다. 질의마다 bm25Search와 projectSearch의 순위로 reciprocalRank를 구하고 평균 MRR과 pairedBootstrap 구간을 출력한다. 질의를 결과를 보기 전에 써야 하는 이유를 몸으로 느끼는 과제.
과제 6. nprobes별 재현율 곡선
buildIvf로 시드 3개를 만들고, nprobes 1~8에서 평균 Recall@10과 평균 scanned를 표로 출력한다. 시드 간 차이가 가장 큰 nprobes는 어디인가?
과제 7 (설계). 이 프로젝트 Indexer를 진짜 BM25로
src/shared/indexing/Indexer.ts의 역색인을 Map<token, Map<filePath, tf>>로 바꾸고 문서 길이를 저장하는 설계를 쓴다. removeFileEntries와 증분 업데이트에서 평균 길이를 어떻게 갱신할지, 태그·제목 같은 필드를 어떻게 다룰지, 평가셋으로 무엇을 비교할지까지 적는다.
