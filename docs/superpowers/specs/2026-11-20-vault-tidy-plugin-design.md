# Vault 정리 플러그인 설계: 병렬 작업 단위

## 1. 왜 바꾸는가

이 프로젝트는 "Obsidian Vault를 AI가 검색하는 MCP 서버"로 출발했지만, 실제로 해결하려던 고통은 검색이 아니었다.

- frontmatter를 직접 쓰는 일
- 이미지가 노트 사이에 아무렇게나 쌓이는 일
- 폴더 구조를 잡는 일
- AI에게 내 경험과 맥락을 매번 다시 설명하는 일

앞의 셋은 노트를 쓴 뒤 따라오는 관리 노동이고, 넷째는 그 관리가 안 된 결과다. 경험 관련 노트가 일곱 곳에 흩어져 있으면 AI도 무엇이 원본인지 알 수 없다.

새 목표는 다음 한 문장이다.

> 노트를 쓰고 난 뒤의 관리 노동을 AI가 대신하고, 그렇게 정리된 Vault를 AI가 내 맥락을 파악하는 근거로 쓴다.

형태는 **Claude Code 플러그인**이다. 클라이언트(모델, 대화, 컨텍스트 관리)는 Claude Code를 그대로 쓰고, 이 저장소는 다음 세 가지만 제공한다.

| 구성 | 역할 |
|---|---|
| MCP 서버 | 항상 같게 동작해야 하는 손발: 파일 스캔, 링크 해석, 링크를 보존하는 이동, 되돌리기, 검색 인덱스 |
| Skill | 사용자의 규칙과 정리 절차: 승인 흐름, 이름 짓기, 판단 기준 |
| Hook | 안전장치: Claude가 셸로 Vault 파일을 직접 옮기거나 지우지 못하게 막음 |

## 2. 실제 Vault에서 확인한 문제

사용자 Vault 트리(2026-11-20 기준)를 파일명으로 본 결과다. 내용 비교는 아직 하지 않았다.

| 문제 | 예 |
|---|---|
| 같은 이름의 노트와 이미지가 여러 곳에 있음 | `스터디/HTTP.md`와 `스터디/1주차/HTTP.md`, `Pasted image 20250122*.png`가 `스터디/`와 `스터디/5주차/`에 각각 있음 |
| 이미지 정리 방식이 다섯 가지 섞여 있음 | 노트 옆에 섞임(`AI/빅분기/`에 약 60장), `첨부파일/` 하위 폴더, 루트 `images/<노트명>/`, `sunub/image/`, `sunub/images/` |
| 무제 노트 | `무제.md`, `무제 12.md` 등 20개 이상 |
| 빈 폴더 | `무제/`, `sunub/스터디/`, `images/알고리즘/` |
| 같은 이름 노트가 많아 링크가 모호함 | `자기소개서.md` 5개 이상, `무제.md`, `HTTP.md` |
| 이 프로젝트가 남긴 흔적 | 루트 `memory/`(`collect_context` 스냅샷), `images/이미지 정리 테스트/` |

## 3. 목표, 비목표, 실패 조건

### 목표 (이 문서의 범위: 1단계 "폴더 안 정돈")

- 이미지를 같은 폴더의 `attachments/` 하위 폴더로 모은다.
- 내용이 완전히 같은 중복 노트와 이미지를 찾아 하나만 남긴다.
- 무제 노트를 정리한다. 빈 노트는 지우고, 내용이 있는 노트는 Claude가 제안한 제목으로 바꾼다.
- 빈 폴더를 정리한다.
- 모든 변경을 미리보기로 보여주고, 승인 후 실행하고, 한 번에 되돌릴 수 있게 한다.
- 이 기반(스캔, 링크 해석, 계획 실행, 되돌리기)을 2단계 주제별 재구성이 그대로 재사용할 수 있게 만든다.

### 비목표

- 이력서, 자기소개서 같은 특정 문서 작업 기능. 이력서는 동기를 설명하는 예시일 뿐이다.
- Obsidian 플러그인, 모바일, 외부 MCP 클라이언트 전용 기능.
- 노트를 저장할 때마다 자동으로 정리하기. Hook은 Obsidian 저장 이벤트를 받지 못한다.
- 서버 안에서 LLM을 호출하는 일. 판단이 필요한 부분은 Claude가 한다.

### 실패 조건 (기술적으로 동작해도 실패로 본다)

- 정리 후 깨진 링크가 하나라도 생긴다.
- 최상위 폴더 경계를 넘어 노트가 옮겨진다.
- 사용자가 보지 못한 변경이 실행된다.
- 되돌리기 후 원래 상태와 다르다.
- 정리 도구가 Vault 안에 사용자가 읽을 수 있는 부산물을 남긴다. `memory/` 같은 경우를 다시 만들지 않는다.

## 4. 정리 규칙

### 4.1 최상위 폴더 경계

- **최상위 폴더**는 Vault 루트의 바로 아래 폴더다(`sunub/`, `스터디/`, `AI/` 등).
- 최상위 폴더 자체의 이름 변경, 삭제, 병합은 하지 않는다.
- 최상위 폴더 안의 **노트**는 그 폴더 안에서만 움직인다. 하위 폴더는 새로 만들거나 비면 지울 수 있다.
- **첨부 파일**은 자신을 참조하는 노트를 따라간다. 참조하는 노트가 모두 같은 최상위 폴더에 있으면 그 폴더로 옮길 수 있다. 루트 `images/<노트명>/`처럼 이 프로젝트의 이전 도구가 노트와 떨어뜨려 놓은 이미지를 되돌리기 위한 규칙이다.
- 루트에 직접 있는 파일은 어느 최상위 폴더로든 옮길 수 있다. 항목별 승인을 받는다.
- 이 규칙은 Skill이 아니라 **서버 코드가 강제한다.** 규칙을 어기는 계획은 실행 단계에서 거부한다.

### 4.2 위험도 단계

| 단계 | 대상 | 승인 방식 |
|---|---|---|
| `bulk` | 이미지를 첨부 폴더로 이동, 루트 `images/<노트>/`의 이미지를 노트 옆으로 되돌리기, 빈 폴더 삭제 | 계획 전체를 한 번에 승인 |
| `per_item` | 중복 삭제, 빈 무제 노트 삭제, 무제 노트 이름 변경, 루트 노트 이동 | 항목별로 선택 |
| `report` | 이름은 같고 내용이 다른 노트, 어디서도 참조하지 않는 이미지, 서로 다른 최상위 폴더의 노트들이 함께 쓰는 이미지 | 실행하지 않고 알리기만 함 |

### 4.3 삭제

삭제는 실제로 지우지 않고 Vault의 `.trash/`로 옮긴다. Obsidian이 "Move to Obsidian trash" 설정에서 쓰는 위치와 같다. 되돌리기 기록에도 남는다.

## 5. 접근 방식

1단계 정돈을 만드는 방식으로 세 가지를 검토했다.

| 방식 | 내용 | 장단점 |
|---|---|---|
| A. 기존 도구 확장 | `organize_attachments`에 옵션을 더하고 중복, 무제 도구를 하나씩 추가 | 빠르지만 각 도구가 이동, 링크 갱신, 되돌리기를 따로 구현한다. 지금 `organize_attachments`가 그렇게 만들어져서 마크다운 링크 갱신 누락, 공유 이미지 링크 깨짐, 되돌리기 없음 문제가 있다. |
| B. 계획과 실행 분리 (선택) | 각 정돈 기능은 "변경 계획"만 만드는 순수 함수다. 이동, 링크 갱신, 경계 검사, 되돌리기는 공용 실행기 하나가 맡는다 | 안전 규칙이 한 곳에 모인다. 계획을 만드는 함수는 파일 시스템 없이 테스트할 수 있다. 계약만 먼저 정하면 작업 단위를 병렬로 나눌 수 있다. 2단계 재구성도 계획만 새로 만들면 된다. |
| C. Claude가 직접 처리 | MCP는 조회만 하고 Claude가 파일을 옮김 | 서버 코드는 가장 적지만, 링크 갱신과 경계 규칙을 Claude가 매번 지켜야 한다. 실패 조건을 막을 수 없다. |

**B를 선택한다.** 이유는 세 가지다. 실패 조건을 코드로 막을 수 있고, 병렬 작업이 가능하며, 2단계 재사용성이 높다.

## 6. 구조

### 6.1 흐름

```
Claude (Skill: vault-tidy 절차)
  │ 1. tidy_plan 호출
  ▼
MCP: 스캔 → 링크 그래프 → 정돈 플래너들 → 변경 계획 + 미리보기 (planId)
  │ 2. Claude가 미리보기를 사용자에게 표로 보여주고 승인 범위를 받음
  ▼
MCP: plan_apply(planId, 승인된 항목)
  │    검증(경계, 충돌, 계획 이후 파일 변경 여부) → 이동/삭제 → 링크 재작성 → 실행 기록
  ▼
필요하면 plan_undo(runId)
```

### 6.2 폴더 배치 (CLAUDE.md 규칙 기준)

| 위치 | 내용 | 이유 |
|---|---|---|
| `src/shared/vault-ops/` | 계약 타입, 스캐너, 링크 해석기, 계획 실행기, 실행 기록 | `tidy`와 `plan` 두 기능이 처음부터 함께 쓰고, 2단계 재구성도 쓴다. `src/utils`를 import하지 않으며 Vault 경로는 인자로 받는다. |
| `src/tools/tidy/` | 정돈 플래너 네 개와 `tidy_plan` 도구 | 기능 하나 |
| `src/tools/plan/` | `plan_apply`, `plan_undo` 도구 | 정돈과 재구성이 함께 쓰는 실행 진입점 |
| `plugin/` | 플러그인 매니페스트, Skill, Hook | 서버 코드와 독립 |
| `tests/unit/` | 단위 테스트 | 기존 규칙 |
| `tests/fixtures/messy-vault/` | 실제 Vault 모양을 본뜬 가짜 Vault | 모든 단위가 같은 입력으로 테스트 |

### 6.3 계약 (단위 P0에서 확정)

병렬 작업의 기준이 되는 타입이다. 이름과 필드는 P0에서 바뀔 수 있지만, 확정 후에는 바꾸지 않는다. 확정본은 `docs/superpowers/plans/2026-11-20-vault-tidy/P0-contracts.md`이며, 아래와 다르면 P0 문서를 따른다. 특히 플래너는 노트 본문을 읽어야 하므로 `Planner`는 `readNote`를 받는 비동기 함수로 바뀌었다.

```ts
type VaultFile = {
  path: string;
  kind: "note" | "attachment" | "other";
  size: number;
  hash: string;
  mtimeMs: number;
};

type VaultSnapshot = {
  root: string;
  files: VaultFile[];
  folders: string[];
  emptyFolders: string[];
};

type LinkRef = {
  from: string;
  raw: string;
  target: string;
  form: "wiki" | "embed" | "markdown" | "markdown-embed";
  suffix: string;
  resolved: string | null;
  ambiguous: boolean;
};

type LinkGraph = {
  refs: LinkRef[];
  inbound(path: string): LinkRef[];
  outbound(path: string): LinkRef[];
};

type RiskTier = "bulk" | "per_item" | "report";

type PlanOp =
  | { id: string; type: "move"; from: string; to: string; tier: RiskTier; reason: string }
  | { id: string; type: "trash"; path: string; tier: RiskTier; reason: string }
  | { id: string; type: "removeEmptyFolder"; path: string; tier: RiskTier; reason: string }
  | { id: string; type: "report"; paths: string[]; tier: "report"; reason: string };

type ChangePlan = {
  planId: string;
  createdAt: string;
  source: string;
  ops: PlanOp[];
  fileHashes: Record<string, string>;
};

type Planner = (snapshot: VaultSnapshot, graph: LinkGraph, options: TidyOptions) => PlanOp[];

type ApplyResult = {
  runId: string;
  applied: string[];
  rejected: { opId: string; reason: string }[];
  rewrittenLinks: number;
};
```

이름 변경은 같은 폴더 안의 `move`로 표현한다. `report`는 실행기가 무시한다.

### 6.4 실행기의 보장

- **경계 검사:** 4.1 규칙을 어기는 `move`는 거부한다.
- **오래된 계획 거부:** 계획에 포함된 파일의 해시가 계획 시점과 다르면 해당 연산을 거부한다.
- **충돌 처리:** 목적지에 파일이 있으면 거부한다. 덮어쓰지 않는다.
- **링크 재작성:** 옮긴 파일을 가리키는 모든 링크를 다시 쓴다. 별칭(`|`), 제목(`#`), 이미지 크기(`|300`) 같은 접미사를 보존한다. 옮긴 뒤 파일명이 모호해지면 경로를 포함한 링크로 쓴다. 옮겨진 노트 안의 상대 경로 마크다운 링크도 고친다.
- **실행 기록:** 실행마다 연산과 링크 변경 전후 내용을 Vault의 `.vault-tidy/runs/<runId>.json`에 남긴다. 점으로 시작하는 폴더라 Obsidian에 보이지 않는다.
- **되돌리기:** 실행 기록을 역순으로 적용한다. 되돌리기 전에도 현재 파일 해시를 확인한다.
- **재색인:** 따로 호출하지 않는다. `VaultWatcher`가 이동을 삭제와 추가로 받아 검색 인덱스를 갱신하고, 점으로 시작하는 폴더(`.trash/`, `.vault-tidy/`)는 무시한다. 그래서 도구가 `src/utils`를 import할 필요가 없다.

## 7. 작업 단위

### 7.1 의존 관계

```
P0 계약 ─┬─► A1 스캐너 ──────────┐
         ├─► A2 링크 해석기 ─────┼─► A3 계획 실행기 ─► C2 apply/undo 도구 ─┐
         ├─► T0 테스트용 Vault   │                                         │
         ├─► B1 첨부 플래너 ─────┤                                         ├─► I 통합 검증
         ├─► B2 중복 플래너 ─────┼─► C1 tidy_plan 도구 ────────────────────┤
         ├─► B3 무제 플래너 ─────┤                                         │
         ├─► B4 빈 폴더 플래너 ──┘                                         │
         ├─► D 플러그인(Skill, Hook) ──────────────────────────────────────┘
         └─► E 기존 코드 정리 (독립)
```

**P0만 순서대로 먼저 하고, 그다음은 모두 동시에 시작할 수 있다.** A3, C1, C2는 의존 대상의 실제 구현 대신 계약 타입으로 만든 가짜 구현으로 먼저 작업하고, 통합은 I에서 한다.

### 7.2 단위 목록

각 단위는 하나의 브랜치 또는 PR이다. 완료 기준은 해당 테스트 통과와 `npm run build` 성공이다.

#### P0. 계약 확정 (선행)

- **산출물:** `src/shared/vault-ops/types.ts`(6.3의 타입), 각 함수의 시그니처만 있는 빈 모듈, `TidyOptions`(첨부 폴더 이름, 기본값 `attachments` 등).
- **완료 기준:** 빌드 성공, 다른 단위 담당자가 이 파일만 보고 작업을 시작할 수 있음.
- **크기:** 작음.

#### T0. 테스트용 Vault

- **산출물:** `tests/fixtures/messy-vault/`. 2장의 문제를 모두 담는다. 같은 이름과 같은 내용, 같은 이름과 다른 내용, 다섯 가지 이미지 배치, 빈 무제와 내용 있는 무제, 빈 폴더, 모호한 `[[자기소개서]]` 링크, 크기 지정 이미지 링크, 마크다운 링크와 공백 인코딩 경로, 두 최상위 폴더가 함께 쓰는 이미지가 들어간다. 개인 내용은 넣지 않는다.
- **완료 기준:** 각 사례가 어떤 기대 결과를 갖는지 `tests/fixtures/messy-vault/EXPECTED.md`에 표로 적음.
- **크기:** 작음.

#### A1. Vault 스캐너

- **위치:** `src/shared/vault-ops/scan.ts`
- **산출물:** 노트, 첨부, 기타 파일을 모두 걷고 해시와 빈 폴더를 계산해 `VaultSnapshot`을 만든다. 기존 `DirectoryWalker`는 `.md`만 보므로 쓰지 않는다. `.obsidian/`, `.trash/`, `.vault-tidy/`, `.git/`은 제외한다.
- **완료 기준:** T0에 대한 스냅샷 테스트.
- **크기:** 작음.

#### A2. 링크 해석기

- **위치:** `src/shared/vault-ops/links.ts`
- **산출물:** 링크 파싱(위키, 임베드, 마크다운, 마크다운 이미지, 별칭, 제목, 크기, URL 인코딩)과 Obsidian 방식의 해석(정확한 경로, 고유한 파일명, 모호함 판정)으로 `LinkGraph`를 만든다. 링크 하나를 새 대상으로 다시 쓰는 함수도 포함한다.
- **참고:** `src/utils/processor/LinkExtractor.ts`는 크기 접미사와 마크다운 링크 경로 해석이 부족하다. 새 코드를 shared에 쓰고, 기존 파일은 E 또는 2단계에서 대체한다.
- **완료 기준:** 형태별 파싱과 재작성 왕복 테스트, T0의 모호 링크 판정 테스트.
- **크기:** 중간. 1단계에서 가장 까다로운 단위다.

#### A3. 계획 실행기와 실행 기록

- **위치:** `src/shared/vault-ops/apply.ts`, `journal.ts`, `boundary.ts`
- **산출물:** 6.4의 보장 전부. 계획 저장과 조회(planId, `.vault-tidy/plans/<planId>.json`에 저장해 서버가 재시작돼도 유지), 승인된 연산만 실행, 되돌리기.
- **의존:** A2의 재작성 함수. 그 전까지는 가짜 구현으로 작업한다.
- **완료 기준:** T0 복사본에 실행 → 깨진 링크 0개 → 되돌리기 → 원본과 해시가 모두 같음. 경계 위반, 오래된 계획, 목적지 충돌을 각각 거부하는 테스트.
- **크기:** 중간.

#### B1. 첨부 플래너

- **위치:** `src/tools/tidy/planners/attachments.ts`
- **규칙:** 이미지는 그 이미지를 참조하는 노트 폴더의 첨부 폴더로 옮긴다. 여러 노트가 참조하면 첫 노트의 폴더로 옮기되, 참조하는 노트들이 서로 다른 최상위 폴더에 있으면 옮기지 않고 `report`로 남긴다. 루트 `images/<노트명>/`의 이미지는 노트 옆 첨부 폴더로 되돌린다. 아무도 참조하지 않는 이미지는 `report`로 남긴다. 이미 `attachments/`에 있으면 건드리지 않는다. 기존 `첨부파일/` 폴더의 이미지는 같은 위치의 `attachments/`로 옮겨 이름을 통일하고, 비게 된 `첨부파일/`은 B4가 지운다.
- **완료 기준:** T0에 대한 계획 결과 테스트.
- **크기:** 작음.

#### B2. 중복 플래너

- **위치:** `src/tools/tidy/planners/duplicates.ts`
- **규칙:** 해시가 같은 파일끼리 묶는다. 들어오는 링크가 가장 많은 파일을 남기고, 같으면 더 깊은 경로(이미 하위 폴더로 분류된 쪽)를, 그것도 같으면 최근 수정본을 남긴다. 나머지는 `trash`(`per_item`)로 처리하고 남는 파일로 링크를 옮긴다. 이름이 같고 내용이 다르면 `report`로 남긴다. 내용이 비어 있는 파일은 B3이 다루므로 묶지 않는다.
- **완료 기준:** T0 테스트. 남길 파일 선택 규칙의 경우마다 테스트.
- **크기:** 작음.

#### B3. 무제 플래너

- **위치:** `src/tools/tidy/planners/untitled.ts`
- **규칙:** `무제`, `무제 N`, `Untitled`, `Untitled N` 노트가 대상이다. 본문이 비었거나 frontmatter만 있으면 `trash`(`per_item`)로 처리한다. 내용이 있으면 "제목 필요" 항목으로 미리보기를 붙여 돌려준다. Claude가 제목을 제안하면 같은 폴더 안 `move`가 된다.
- **추가 계약:** `tidy_plan` 결과에 `needsTitle: { path, preview }[]`를 넣고, `plan_apply`가 `renames: { path, title }[]`를 받아 계획에 이름 변경을 더한다. 이름이 겹치면 거부한다. P0에서 함께 확정한다.
- **완료 기준:** T0 테스트.
- **크기:** 작음.

#### B4. 빈 폴더 플래너

- **위치:** `src/tools/tidy/planners/empty-folders.ts`
- **규칙:** 비어 있는 하위 폴더를 `removeEmptyFolder`(`bulk`)로 처리한다. 최상위 폴더는 비어 있어도 지우지 않고 `report`로 남긴다. 다른 연산이 실행된 뒤 비게 되는 폴더는 실행기가 마지막에 다시 계산한다.
- **크기:** 아주 작음.

#### C1. `tidy_plan` 도구

- **위치:** `src/tools/tidy/index.ts`, `params.ts`
- **산출물:** 스캔 → 링크 그래프 → 플래너 실행 → 계획 저장 → 단계별로 묶은 미리보기 반환. 입력은 범위(전체 또는 최상위 폴더 하나)와 포함할 플래너 목록이다. 응답에는 Claude가 표로 보여주기 좋은 요약(연산 수, 갱신될 링크 수, 비게 될 폴더)을 넣는다. 플래너는 중복, 무제, 첨부, 빈 폴더 순으로 실행하고, 앞선 플래너가 이미 다룬 경로를 건드리는 뒤 플래너의 연산은 버린다.
- **완료 기준:** T0에 대해 도구를 호출하는 테스트.
- **크기:** 작음.

#### C2. `plan_apply`, `plan_undo` 도구

- **위치:** `src/tools/plan/`
- **산출물:** 승인된 연산 id 목록과 이름 변경 목록을 받아 A3을 호출한다. `plan_undo`는 runId를 받는다. 실행 후 검색 인덱스를 한 번 갱신한다.
- **완료 기준:** 도구 수준의 실행과 되돌리기 테스트.
- **크기:** 작음.

#### D. 플러그인 포장, Skill, Hook

- **위치:** `plugin/`
- **산출물:**
  - 플러그인 매니페스트와 MCP 서버 등록(npx 실행, `VAULT_DIR_PATH`).
  - Skill `vault-tidy`: 언제 쓰는지, `tidy_plan` → 미리보기 표 → 단계별 승인(`bulk`는 한 번, `per_item`은 목록 선택, `report`는 안내만) → `plan_apply` → 결과와 되돌리기 방법 안내까지의 절차. 무제 노트 제목 짓는 규칙(본문 핵심 주제, 같은 폴더 이름과 겹치지 않게)도 담는다.
  - Hook: Claude가 Bash로 Vault 경로 아래 파일에 `mv`, `rm`, `cp`를 실행하려 하면 막고 정돈 도구를 쓰라고 안내한다.
- **의존:** 도구 이름과 입력 형태(P0)만 필요하다.
- **주의:** 플러그인 디렉터리 구조와 Hook 설정 형식은 구현 시점의 Claude Code 공식 문서로 확인한다.
- **완료 기준:** 로컬에서 플러그인을 설치해 T0 복사본에 정돈 절차를 끝까지 실행하고, Hook이 `mv`를 막는 것을 확인.
- **크기:** 중간.

#### E. 기존 코드 정리 (독립)

방향 전환으로 필요 없어진 코드를 지운다. 서로 독립적이라 E1~E4로 더 나눠도 된다.

- **E1.** 개발용 CLI(`src/cli/`, `npm run cli`, CLI 전용 테스트와 벤치마크, Ink 관련 의존성), `src/utils/LLMClient.ts`, `LLM_API_URL`과 `LLM_CHAT_MODEL` 설정과 서버 안내문의 해당 줄.
- **E2.** `collect_context`의 Vault 쓰기(`memoryMode` 중 `vault_note`, `both`)와 `load_memory`. 사용자 Vault의 `memory/` 폴더는 사용자가 직접 지운다.
- **E3.** `generate_property`, `create_document_with_properties`를 도구에서 빼고, 담고 있던 지시문을 3단계 frontmatter Skill의 초안으로 `docs/`에 옮긴다.
- **E4.** `organize_attachments`를 지운다. B1과 C가 대체하므로 I가 끝난 뒤에 진행한다.
- **주의:** `src/tools/index.ts`, `src/server.ts`, `package.json`은 C1, C2, E가 함께 고친다. 충돌은 작지만 병합 순서를 C → E로 둔다.

#### I. 통합 검증

- T0 복사본에 플러그인 절차 전체를 실행한다: 정돈 → 깨진 링크 0개 확인 → 되돌리기 → 원본과 같음 확인.
- 사용자의 실제 Vault 복사본에 `tidy_plan`만 실행해 미리보기를 사람이 검토한다. 실제 Vault에 실행하는 것은 사용자가 정한다.

## 8. 이후 단계 (이 문서에서 설계하지 않음)

- **2단계, 주제별 재구성과 허브 노트:** 최상위 폴더 하나 안에서 임베딩으로 비슷한 노트 묶음을 찾고, Claude가 하위 폴더 구조와 이름을 제안하면 같은 `ChangePlan`으로 실행한다. 폴더를 넘나드는 흩어짐은 허브 노트를 만드는 새 연산으로 잇는다. 임베딩과 벡터 검색 코드가 `src/utils`에 있어 기능 폴더가 바로 쓸 수 없으므로, 필요한 부분을 shared로 옮기는 범위를 그때 정한다.
- **3단계, frontmatter 규칙:** 블로그 글(`slug`, `date`, `category`)과 일반 노트를 다른 규칙으로 다룬다. Vault에 이미 쓰인 태그와 속성값을 조회하는 도구와 Skill로 구성한다.
- **4단계, 남은 정리:** `vault` 통합 도구를 기능별 도구로 나누고, 저장소 이름과 README를 새 정체성에 맞게 바꾼다.

## 9. 설계자가 정한 것 (사용자 확인 필요)
