# 검색 품질 평가: 1차 검출(키워드 + 벡터 RRF) → AI 재판정(리랭커)

`scripts/eval_retrieval.ts`와 `scripts/eval_retrieval_diagnose.ts`로 측정한 결과입니다.

## 조건

- 데이터: KLUE-MRC v1.1 dev (CC BY-SA 4.0). 문단 5,310개를 노트 한 개씩으로 만든 Vault. 질문의 정답은 그 질문이 만들어진 문단입니다.
- 질의: 답이 있는 질문 중 type 1(패러프레이즈) 100개, type 2(다중 문장 추론) 100개. seed 42.
- 모델: `Xenova/paraphrase-multilingual-MiniLM-L12-v2`(임베딩), `Xenova/bge-reranker-base`(리랭커). `setup`이 받는 기본 파일(fp32).
- 실행 환경: 4코어 CPU 클라우드 컨테이너. 지연 시간은 이 환경 기준입니다.
- 검색 코드는 빌드된 서버 코드(`build/`)를 그대로 호출합니다. 벡터 인덱스는 `RAGIndexer.indexAll` 경로로 만든 뒤 서버와 같은 IVF-PQ 인덱스를 생성했습니다.

## 단계별 결과 (질의 200개, top-10)

| 단계 | Hit@1 | Hit@10 | 미검률@10 | MRR@10 | 평균 지연 |
|---|---|---|---|---|---|
| 키워드 단독 (AI 불가 시 폴백) | 30.0% | 31.5% | 68.5% | 0.307 | 0.5ms |
| 벡터 단독 (재판정 없음) | 7.5% | 19.5% | 80.5% | 0.106 | 113ms |
| 1차 검출: 키워드 + 벡터 RRF | **32.5%** | **43.0%** | **57.0%** | **0.359** | 130ms |
| 1차 검출 + AI 재판정 (실제 서버 경로) | 11.0% | 23.0% | 77.0% | 0.148 | 14,643ms |

질문 유형별로 보면 키워드는 패러프레이즈(Hit@10 21.0%)에, 벡터는 다중 문장 추론(11.0%)에 약했습니다. RRF는 두 유형 모두에서 각 단독 방식보다 높았습니다(37.0%, 49.0%).

## AI 재판정 효과 (RRF 결과 대비, 질의 단위)

| 1순위 변화 | 질의 수 |
|---|---|
| 1차 오답 → 재판정 후 정답 (바로잡음) | 3 |
| 1차 정답 → 재판정 후 오답 (오판) | 46 |
| 둘 다 정답 | 19 |
| 둘 다 오답 | 132 |

- 상위 10개 안에 있던 정답이 밖으로 밀려난 질의 45건, 밖에서 안으로 들어온 질의 5건.
- 벡터 1위 거리가 0.2 미만이라 재판정을 생략한 질의(30건)의 Hit@1은 36.7%, 재판정한 질의(170건)는 6.5%.
- 실제 서버 경로 처리 시간의 99.1%가 리랭커입니다(질의당 문서 110개 판정: 벡터 쪽 90개 + RRF 이후 20개).

## 원인 분리 (`eval_retrieval_diagnose.ts`)

### 1. 리랭커 입력 결함

`VaultManager.hybridSearch()`는 리랭커에 각 후보의 `matchedChunks[0].content || frontmatter.summary || filePath`를 넘깁니다. 키워드로만 찾은 문서는 벡터 청크가 없으므로 **본문 대신 파일 경로로 판정**됩니다. 정답이 RRF 후보(최대 20개)에 들어간 질의 91건 중 41건(45%)에서 정답이 이런 문서였습니다.

RRF 이후 재판정만 켜고(벡터 내부 재판정은 끔) 리랭커 입력만 바꿨을 때:

| 리랭커 입력 | Hit@1 | Hit@10 | MRR@10 | 바로잡음 / 오판 |
|---|---|---|---|---|
| 현재 코드 그대로 (평가 Vault 파일명은 `klue_12_0.md` 같은 ID) | 12.0% | 27.5% | 0.162 | 3 / 44 |
| 파일명을 노트 제목으로 바꾼 경우 (실제 Vault에 가까운 조건) | 14.5% | 32.5% | 0.198 | 3 / 39 |
| 본문 앞 1,500자를 넣은 경우 | 21.5% | 40.0% | 0.272 | 4 / 26 |
| (비교) 재판정 없음 = RRF | 32.5% | 43.0% | 0.359 | - |

입력을 본문으로 고치면 크게 회복하지만 **여전히 RRF보다 낮습니다.** 입력 결함 외에 리랭커 모델 자체가 이 데이터(한국어)에서 1차 순위를 개선하지 못한다는 뜻입니다. `bge-reranker-base`는 영어·중국어 중심 모델이므로 언어 적합성이 유력한 원인이지만, 다국어 리랭커로 교체한 비교는 아직 하지 않았습니다.

### 2. 임베딩 질의 접두어 불일치

서버는 질의에 `search_query: `, 문서에 `search_document: ` 접두어를 붙입니다. 이는 예전에 쓰던 nomic 임베딩 모델의 규칙이고 현재 모델(MiniLM)과는 맞지 않습니다.

| 벡터 단독 조건 | Hit@10 |
|---|---|
| IVF-PQ 인덱스 (서버 기본) | 19.5% |
| 정확 검색 | 22.0% |
| 정확 검색 + 질의 접두어 제거 (문서 쪽 접두어는 그대로) | 30.0% |

### 3. 키워드 검색의 질의 토큰화

질의를 공백으로만 나눠 문장부호와 조사가 붙은 채 매칭합니다. 질문 4,008개 전체 기준으로 51.8%가 결과 0건이었고, 질의를 문서와 같은 규칙으로 토큰화하면 Hit@10이 30.1%에서 35.4%로 올랐습니다.

### 4. 백그라운드 인덱싱 속도

`syncMissingRagIndices()`는 파일마다 두 테이블에 delete + add를 반복합니다. 문서 5,310개 중 2시간 동안 3,489개만 처리했고(테이블 버전 약 7,000개, 2.3GB), 같은 청킹·임베딩 코드를 50개 배치로 쓰는 `indexAll()`은 905초에 끝났습니다.

## 한계

- 공개 뉴스·위키 문단과 완전한 문장 질문입니다. 개인 노트와 에이전트가 보내는 짧은 키워드 질의와는 분포가 다릅니다. 특히 키워드 검색에는 불리한 조건입니다.
- 질의 200개 표본이라 비율에 수 % 포인트의 오차가 있습니다.
- 평가 Vault의 파일명이 ID라서 리랭커 입력 결함의 영향이 실제보다 큽니다. 제목 파일명 조건으로 이를 보정한 수치를 함께 적었습니다.

## 재현

```bash
npm install && npm run build
npx @sunub/obsidian-mcp-server setup          # 로컬 모델 설치
npm run eval:retrieval -- --sample 100 --out .eval-cache/full
npx tsx scripts/eval_retrieval_diagnose.ts .eval-cache/full
```
