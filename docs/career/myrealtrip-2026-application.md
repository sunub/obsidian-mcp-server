# 마이리얼트립 2026 신입 공개채용 지원서 정리 — Obsidian MCP Server

> 이 문서는 마이리얼트립 공고·FAQ·밋업 정리글을 기준으로 "무엇을 보여줘야 하는지"를 먼저 정리하고,
> 그 기준에 맞춰 `obsidian-mcp-server` 프로젝트의 실제 코드, `docs/` 문서, 커밋 이력(2025-09-04 ~ 2026-07-06, 129개 커밋, PR #2 ~ #65)에서
> 근거를 뽑아 경험을 재구성한 것입니다. 마지막에 그대로 다듬어 제출할 수 있는 **자유 양식 초안**을 붙였습니다.

## 1. 공고가 가장 중요하게 보는 것

### 한 문장 요약

> **"정답이 없는 문제를 스스로 발견해서, 근거를 갖고 판단하고, 막히면 방법을 바꿔서라도 끝까지 가서, 실제로 무언가를 해결한 사람"**

공고 문장들을 겹쳐 보면 평가 기준은 결국 하나로 모입니다. 직무 역량, 경험의 규모, 만든 것의 목록은 보지 않겠다고 여러 번 말합니다.
대신 문제를 **자기 것으로 받아들이고 결과까지 책임지는 방식**을 봅니다.

| 공고/밋업에서 반복된 메시지 | 실제로 의미하는 평가 포인트 |
| --- | --- |
| "창업가처럼 일한다" = 역할에 경계를 두지 않고, 문제를 자신의 것으로 받아들여 결과를 낸다 | **오너십**: 시킨 일이 아니라 내가 발견한 문제인가 |
| 고객의 문제는 직무로 나뉘어 오지 않는다 → 한 사람이 문제를 처음부터 끝까지 맡는다 | **End-to-End**: 내 파트가 아니라 문제 전체(발견→해결→결과)를 보여줬는가 |
| 무엇을 만들었는지보다 **무엇이 해결됐는지** | **결과 중심**: "그래서 누구의 어떤 문제가 풀렸는가"가 있는가 |
| 정답이 없어도 판단하고 **검증**하는 사람 | **근거와 검증**: 왜 그 선택을 했고, 맞았는지 어떻게 확인했는가 |
| 방법을 바꿔서라도 **끝을 보는** 사람 | **회복력**: 막혔을 때 포기 대신 경로를 바꾼 경험이 있는가 |
| 필요한 것을 빠르게 배우는 사람 / AI를 **도구**로 써서 결과를 낸 경험 | **학습 속도**: 처음 하는 일을 무엇으로, 얼마나 빨리 배워 결과를 냈는가 |
| 작게 시작해 끝까지 간 경험 | **완주**: 작은 시도가 실제 결과물(배포, 사용)까지 이어졌는가 |

### 서류에서 지켜야 할 형식

밋업 정리글이 권한 순서는 **문제 → 근거 → 실행(→ 결과)** 입니다.

1. **문제**: 무엇이 불편/부족했고, 그걸 어떻게 알아차렸는가
2. **근거**: 여러 선택지 중 왜 그것을 골랐고, 무엇이 그 판단을 뒷받침했는가
3. **실행**: 실제로 무엇을 했고, 해보니 어떤 결과가 나왔는가
4. (+ 힌트) 만든 것 뒤에 **"그래서 무엇이 달라졌는지"** 한 줄

### 이 프로젝트로 보여주기 좋은 지점

이 프로젝트는 공고의 기준과 잘 맞습니다. 이유는 세 가지입니다.

- **아무도 시키지 않은 문제에서 시작했다**: 개인 Obsidian 노트를 AI 에이전트가 쓰지 못한다는 내 불편에서 출발했다.
- **배포 후 실제로 드러난 문제를 계속 고쳤다**: npm 배포(v0.0.x → v0.3.29) 이후 실행 불가, 메모리 폭증, 검색 누락, 배포 구조 실패를 하나씩 고쳤다.
- **틀린 판단을 되돌린 기록이 남아 있다**: 모노레포 전환을 롤백했고, 메모리 수정이 만든 새 문제를 다시 설계해 풀었다. "방법을 바꿔서라도 끝을 보는" 장면이 커밋으로 증명된다.

### 에피소드 0. 시작 — "아무도 시키지 않았지만 시작해 본 일"

**문제**
몇 년 동안 Obsidian에 쌓은 학습 노트와 기록이 있는데, AI 에이전트와 일할 때 매번 노트를 복사해 붙여넣어야 했습니다.
내가 이미 정리해 둔 지식을 AI가 모르는 상태로 대화가 시작된다는 점이 반복되는 불편이었습니다.

**실행**
- 2025-09-04 첫 커밋 후 일주일 만에 문서 검색·읽기 도구, frontmatter(속성) 자동 생성/쓰기 도구, E2E 테스트, GitHub Actions CI를 만들었습니다.
- 처음부터 "내 컴퓨터에서만 도는 스크립트"가 아니라 **누구나 `npx`로 설치해 쓰는 npm 패키지**를 목표로 잡았습니다.

**포인트**: 작게 시작했지만 처음부터 "남이 쓸 수 있는 제품"으로 완성하는 것을 목표로 했다는 점.

### 에피소드 1. 토큰 비용 문제 — "필요한 것을 빠르게 배우고, 판단을 검증한 사람"

**문제**
도구가 문서 전체를 그대로 반환하다 보니 AI 클라이언트의 컨텍스트 창이 금방 차고 토큰 비용이 커졌습니다.
도구 하나를 호출할 때마다 응답이 수천 자씩 쌓여 대화가 길어질수록 AI가 앞부분을 잊었습니다.

**근거**
- "검색 결과를 많이 주는 것"과 "AI가 실제로 쓸 수 있는 근거를 주는 것"은 다르다고 판단했습니다. 이 프로젝트의 정체성을 **검색 엔진이 아니라 Agent Context Pipeline**으로 다시 정의했습니다. (`CONTEXT.md`의 용어집: *Context Compression*, *Context Selection Accuracy*)
- 감으로 줄이지 않으려고 **응답마다 추정 토큰, 압축 모드, 잘림 여부, 캐시 적중을 JSONL로 기록하는 계측**부터 넣었습니다. (`src/tools/vault/metrics.ts`, `scripts/vault-metrics-report.mjs`)

**실행** (단계적으로 개선)
1. **2025-09-13 · quiet 모드**: 파일명만 돌려주는 축약 응답부터 시작했습니다.
2. **PR #17 · 압축 정책 체계화**: `compressionMode`(`aggressive`/`balanced`/`none`)별로 결과 개수, 발췌 길이, 백링크 수 상한을 두었습니다.
3. **PR #17 · `collect_context` 액션**(+3,269줄): 여러 문서를 배치로 모아 핵심 사실, 근거 조각, 출처, 미해결 질문을 담은 `memory_packet`으로 압축합니다. 출력 상한을 넘으면 **백링크 → 문서별 글자 수 → 문서 수 → continuation 토큰** 순서로 줄입니다. 한 번에 다 못 담으면 `continuationToken`으로 이어 받고, 같은 요청은 문서 해시 기반 캐시로 재사용합니다. (`docs/collect-context-guide.md`)
4. **PR #61 · 질의 기반 문단 필터링**: `read`에 `query`를 주면 로컬 리랭커가 질문과 가장 관련 있는 문단 3개만 골라 원문 순서대로 돌려줍니다. 잘린 응답에는 AI가 `compressionMode: none`으로 전체를 다시 요청하는 대신 `query` 조회를 하도록 유도하는 힌트를 넣었습니다.
5. **PR #65 · 기본값을 `summary`로**: 계측을 바탕으로 기본 응답을 가장 작은 `summary` 모드로 바꿨습니다. "balanced로 되돌리기"는 컨텍스트 절감 정책과 충돌한다는 이유로 기각했다고 커밋에 남겼습니다.

**결과 / 무엇이 달라졌나**
- AI가 문서 원문 대신 "근거 + 출처"를 받고, 더 필요하면 스스로 이어서 요청하는 구조가 되었습니다.
- 응답 크기 정책은 회귀 테스트로 고정했습니다. (`tests/unit/VaultCompression.test.ts`, `VaultCollectContext.test.ts`, `VaultLoadMemory.test.ts`)

> ✍️ **보완 필요**: `VAULT_METRICS_LOG_PATH`로 쌓은 실제 로그가 있다면 "기본 응답 추정 토큰 N → M" 같은 전후 수치를 한 줄 넣으면 "무엇이 해결됐는지"가 훨씬 선명해집니다.

### 에피소드 2. 외부 AI 의존 문제 — "정답이 없어도 판단하고 검증하는 사람"

**문제**
의미 기반 검색을 붙이려면 임베딩 서버와 리랭커 서버가 필요했습니다. 그런데 개인 노트를 다루는 도구가 외부 서비스나 별도 서버에 의존하면 설치가 어려워지고, 프라이버시 면에서도 맞지 않았습니다.
당시 문서에 이렇게 적었습니다.

> "현재 이 프로젝트가 수행하는 기능들이 외부의 영향이 필요없는 기능들임에도 불구하고 클라이언트 AI를 사용하여 기능을 수행하고 있다는 문제점이 있습니다." — `docs/rules/USING_LOCAL_MACHINE.md`

**근거 (선택지 비교)**
- Elasticsearch 같은 검색 엔진도 검토했습니다. 기술적으로는 충분히 가능한 대안이지만, **"`npx` 한 줄로 끝나는 개인용 패키지"라는 제품 경험과 맞지 않아** 기본값에서 제외했습니다. 불가능해서가 아니라 제품 목표와 맞지 않아서 뺐다는 판단 근거를 `docs/rules/MCP_RAG.md`와 README에 명시했습니다.
- 대신 **임베디드 스택**(LanceDB 로컬 파일 + `transformers.js` 로컬 모델)을 골랐습니다.

**실행**
- **PR #33**: 외부 임베딩/리랭커 서버 의존을 `transformers.js` 로컬 실행으로 옮기고, **키워드 검색 + 벡터 검색을 RRF(Reciprocal Rank Fusion, K=60)로 융합한 뒤 Cross-Encoder 리랭커로 재정렬**하는 하이브리드 검색을 구현했습니다. (`src/utils/VaultManger/VaultManager.ts`의 `hybridSearch`)
- **우아한 성능 저하(Fallback)**: 모델이 없으면 실패하지 않고 키워드 검색으로 동작하며, "setup을 실행하면 하이브리드 검색을 쓸 수 있다"는 안내를 응답에 한 번 붙입니다.
- **비용 대비 효과 판단**: 첫 벡터 결과의 코사인 거리가 0.2 미만으로 이미 충분히 가까우면 비싼 리랭킹을 건너뜁니다.
- **설치 경험 개선(PR #52)**: 복잡하던 에이전트 주도 설치 흐름(-434줄)을 걷어내고 `npx @sunub/obsidian-mcp-server setup` 한 줄로 모델 설치를 끝내게 바꿨습니다.

**결과 / 무엇이 달라졌나**
- 외부 API 키나 별도 서버 없이 사용자 컴퓨터 안에서 의미 기반 검색까지 동작합니다.
- 모델이 없는 사용자도 최소한 키워드 검색은 쓸 수 있어, 설치 장벽 때문에 아예 못 쓰는 경우가 없어졌습니다.

### 에피소드 3. 배포 후 드러난 문제들 — "방법을 바꿔서라도 끝을 보는 사람" ⭐ 핵심

이 프로젝트에서 가장 보여주고 싶은 부분입니다. **만들고 끝이 아니라, 배포하고 나서 터진 문제를 끝까지 따라가 고친 기록**입니다.

#### 3-1. "배포했는데 실행이 안 된다" (2025-09 ~ 2025-11)

- Smithery 배포 시 경로 불일치 문제를 네 번 연속 커밋하며 붙잡았습니다(`fix : Smithery 배포시 경로가 일치하지 않는 문제 수정 중` ×4).
- npm에 배포된 패키지가 `prepare` 스크립트가 없어 실행되지 않는 문제를 PR #3, #4, #6에서 고쳤습니다.
- Vault 경로를 환경 변수로만 받던 방식을 CLI 인자로도 받게 바꿔(#5) 설정 실수를 줄였습니다.
- npm 토큰 방식을 **Trusted Publishing**으로 바꿔(#10, #11) 태그만 푸시하면 CI가 테스트 → 빌드 → 배포 → 릴리스 노트까지 처리하게 했습니다.

#### 3-2. 메모리 45GB 문제 (PR #58)

**문제**: 실제로 사용하던 중 MCP 서버 프로세스의 메모리가 비정상적으로 커졌습니다. 커밋 기록상 **약 45GB까지** 올라갔습니다.

**원인 추적**: "모델이 있는지 확인"하는 `checkModelPresence()`가 호출될 때마다 `pipeline()`으로 **모델을 새로 로드**하고 있었습니다. 인덱싱 중 파일마다 이 함수가 불렸기 때문에 모델 인스턴스가 계속 쌓였습니다.

**실행**
- 모델 확인을 캐싱된 `init()`으로 바꿔 인스턴스가 하나만 존재하게 했습니다.
- 전체 인덱싱을 50개 파일 단위 배치로 나눠 DB에 쓰고 배열을 비우게 했습니다(대형 Vault 인덱싱 중 RAM 스파이크 제거).
- 파일 하나가 바뀔 때 전체 백링크 인덱스를 재빌드하던 구조를 증분 업데이트로 바꿨습니다.
- `SIGINT`/`SIGTERM` 시 워처와 DB 연결을 정리하는 종료 처리를 추가했습니다.

**결과**: 메모리 사용량이 **약 1GB 수준으로 안정화**되었습니다(커밋 메시지 기록 기준).

#### 3-3. 그 수정이 만든 새로운 문제 → 설계부터 다시 (PR #65)

여기서 끝났다면 평범한 버그 수정입니다. 그런데 3-2의 수정이 또 다른 문제를 만들었습니다.

**문제 재발견**
- `checkModelPresence()`가 이제 `init()`을 부르니, **서버가 시작될 때마다 모델 전체를 메모리에 올렸습니다**.
- AI 에이전트는 세션마다 MCP 서버 프로세스를 따로 띄웁니다. 에이전트 창을 여러 개 열면 **모델 사본이 프로세스 수만큼 메모리에 상주**했습니다.
- 에이전트가 종료돼도 stdin EOF나 `SIGHUP` 같은 경로를 감지하지 못해, 백그라운드 인덱싱과 워커 스레드가 남아 있었습니다.

**근거 — 구현 전에 설계 문서부터 작성**
`docs/superpowers/specs/2026-07-05-lazy-local-ai-lifecycle-design.md`에 현재 문제, 목표/비목표, 기각한 대안, 수용 기준을 먼저 정리했습니다.

| 선택지 | 판단 |
| --- | --- |
| 서버 시작 시 모델을 미리 로드 | ❌ 기각: 지금의 메모리 문제를 반복 |
| 모든 검색에서 모델 준비를 10초씩 기다림 | ❌ 기각: 에이전트의 도구 호출 루프가 느려짐 |
| 공유 데몬 프로세스 도입 | ⏸ 1차 범위 밖(비목표): 복잡도 대비 효과가 불확실 |
| **필요할 때만 로드 + 짧은 대기 후 폴백 + 유휴 시 해제** | ✅ 채택 |

**실행**
- `LocalModelManager`(`src/utils/LocalModelManager.ts`): 의미 검색이 실제로 필요할 때만 모델을 로드합니다. **3초 soft deadline** 안에 준비되지 않으면 키워드 결과를 먼저 돌려주고 로딩은 백그라운드에서 이어갑니다. 로딩 자체는 **10초 hard cap**으로 제한합니다. 임베더와 리랭커의 상태를 따로 관리하고, 쓰이지 않으면 해제합니다.
- `ServerLifecycle`(`src/utils/ServerLifecycle.ts`): 루트 `AbortController` 하나로 `SIGINT`/`SIGTERM`/`SIGHUP`/stdin 종료/transport close를 모두 같은 `shutdown()`으로 모았습니다. 여러 번 호출돼도 안전(idempotent)하고, 정리 작업마다 타임아웃을 두어 종료가 무한 대기하지 않습니다.
- `BackgroundTaskRegistry`: fire-and-forget이던 백그라운드 RAG 동기화를 등록해 종료 시 중단·대기할 수 있게 했습니다.
- 각 동작을 테스트로 고정했습니다: `LocalModelLifecycle`, `ServerLifecycle`, `BackgroundTaskRegistry`, `WorkerPoolLifecycle`, `RAGIndexerLifecycle`, `VaultWatcherLifecycle`, `VaultSemanticFallback` 등.

**결과 / 무엇이 달라졌나**
- 서버 시작이 가벼워져, 에이전트 세션을 여러 개 열어도 의미 검색을 쓰기 전까지는 모델이 메모리에 올라가지 않습니다.
- 에이전트를 끄면 인덱싱과 워커가 함께 정리됩니다.
- 모델이 늦게 준비돼도 에이전트는 3초 안에 답을 받습니다.

> ✍️ **보완 필요**: 3-3 이후의 "에이전트 N개 동시 실행 시 idle 메모리" 전후 수치를 직접 측정해 넣으면 3-2(45GB→1GB)와 함께 강력한 결과 지표가 됩니다. 설계 문서의 *Manual verification* 항목이 측정 절차입니다.

#### 3-4. 모노레포 전환 실패와 롤백 (PR #35 → #49)

**판단**: CLI와 서버가 커지면서 공통 코드 관리가 어려워져 `packages/cli`, `packages/server`, `packages/core`의 모노레포로 전환했습니다(PR #35, `commit-message.md`에 배경 기록).

**문제**: 전환 직후 `npx` 배포가 깨졌습니다(#44). 이전 과정에서 LanceDB 버전이 의도치 않게 `^0.27.2` → `^0.10.0`으로 내려갔고, SQL 파서가 `filePath` 컬럼을 소문자로 바꿔 서버 시작 시 `No field named filepath` 오류가 났습니다(#45). 버전 동기화(#46), 공유 의존성 정리(#48)까지 연달아 이어졌습니다.

**방법을 바꿈**: 문제를 하나 고치면 다음 문제가 나오는 상황에서, 원인이 개별 버그가 아니라 **"점진적으로 이전하지 않은 것"** 자체라고 판단했습니다. 그래서 단일 패키지 구조로 **롤백**했습니다(PR #49: "모노레포 환경을 점진적으로 이전하지 않아서 발생하던 오류로 인해 이전 버전으로 롤백").

**배운 것**: 구조 변경은 배포 경로와 함께 작은 단계로 검증해야 합니다. 이 경험 이후 큰 변경(PR #65)은 **설계 문서 → 구현 계획(`docs/superpowers/plans/`) → 집중 테스트** 순서로 진행했습니다.

#### 3-5. 검색 품질 버그를 사용하면서 찾아 고침

| 증상 | 원인 | 수정 |
| --- | --- | --- |
| 관련 문서가 리랭킹 후 결과에서 사라짐 | 리랭커가 돌려준 텍스트의 공백/개행이 원문과 달라 원래 문서로 다시 매핑하지 못함 | 공백 정규화 후 비교 (#59) |

### 에피소드 4. 터미널 AI Agent CLI — "처음 해 보는 일을 빠르게 배워 결과를 낸 경험"

MCP 서버를 검증하려고 로컬 LLM과 연결되는 터미널 AI 에이전트 UI(Ink/React)를 직접 만들었습니다. 터미널 입력 처리는 처음 다뤄 보는 영역이었습니다.

- **한글 입력(IME) 씹힘**: Ink 정식 버전이 React 생명주기에 맞춘 입력을 지원하지 않아 한글이 밀렸습니다. 원인을 찾아 포크 버전(`@jrichman/ink`)으로 교체하고, Ink와 충돌하던 명령형 커서 제어를 선언적 레이아웃으로 바꿨습니다(PR #35).
- **대량 붙여넣기 문제**: Raw mode에서 붙여넣은 텍스트 안의 개행이 Enter로 인식돼 여러 번 전송되는 문제가 있었습니다. 대용량 텍스트가 렌더링을 느리게 만드는 문제도 함께 있었습니다. 이를 설계 문서(`docs/rules/OPTIMIZE_MESSAGE.md`)로 먼저 정리했습니다. 이후 붙여넣기를 하나의 원자적 토큰으로 다루고, **2,000자를 넘는 입력은 임시 파일로 분리해 LLM에는 경로·미리보기·지시문만 보내도록** 구현했습니다(PR #54, `src/cli/services/InputOffloadService.ts`). 벤치마크 스크립트로 확인했습니다(`tests/run_cli_paste_benchmark.ts`).
- **장시간 세션 메모리**: 스트리밍 취소(AbortController), 히스토리 pruning, 완료된 출력을 Ink `<Static>`과 터미널 스크롤백에 넘기는 구조로 렌더링 부담을 줄였습니다(`docs/rules/MEMORY_MANGEMENT.md`).

### 에피소드 5. AI를 "도구"로 쓴 방식 — 밋업 힌트에 직접 대응

공고는 "AI를 도구로 써서 필요한 것을 배우고 결과를 낸 경험"을 묻습니다. 이 프로젝트는 AI를 위한 도구를 만들면서, 동시에 AI 코딩 에이전트를 도구로 써서 만든 프로젝트입니다.

- **AI에게 일을 맡기는 규칙을 설계**: `GEMINI.md`를 최상위 지시문으로 두었습니다. 작업 영역(서버/RAG vs CLI UI)에 따라 읽어야 할 규칙 문서(`docs/rules/*.md`)를 라우팅하고, "변경 범위 밖 리팩터링 금지", "모르면 모른다고 말하기", "실패하면 재시도 전에 원인부터"를 명시했습니다. AI가 엉뚱한 맥락으로 코드를 쓰지 않게 하는 장치입니다.
- **설계는 내가, 구현 보조는 AI가**: PR #65는 AI 코딩 에이전트(Codex)와 함께 진행했습니다. 먼저 설계 문서와 구현 계획을 `docs/superpowers/`에 남겨 판단 근거(제약, 기각한 대안, 신뢰도, 검증 범위)를 고정했습니다. 커밋에는 `Tested`/`Not-tested`를 구분해 무엇을 검증했고 무엇을 아직 검증하지 못했는지 기록했습니다.
- **모르는 영역을 빠르게 배우는 데 활용**: RRF, Cross-Encoder 리랭킹, IVF-PQ 인덱스, 터미널 Bracketed Paste 같은 처음 접한 개념을 AI와 함께 학습했습니다. 이해한 내용은 규칙 문서와 테스트로 남겨, 다음 작업에서 다시 쓸 수 있게 했습니다.

### 내 불편에서 시작해, 배포 후 터진 문제를 끝까지 따라간 10개월

**[문제] 내가 정리한 지식을 AI가 모른다**

저는 [N년간] Obsidian에 학습 노트를 쌓아 왔습니다. AI 에이전트와 일할 때마다 그 노트를 손으로 복사해 붙여넣어야 했고, 대화가 길어지면 AI는 앞의 내용을 잊었습니다. 누가 시킨 일은 아니었지만 매일 겪는 불편이었고, 저 말고도 같은 불편을 겪는 사람이 많을 거라고 생각했습니다. 그래서 2025년 9월, AI 에이전트가 Obsidian 노트를 직접 검색하고 읽을 수 있게 해주는 MCP 서버를 만들기 시작했습니다. 처음부터 목표는 "내 컴퓨터에서만 되는 스크립트"가 아니라 **누구나 `npx` 한 줄로 쓰는 공개 패키지**였습니다.

**[근거] 검색 엔진이 아니라 "AI가 쓸 수 있는 근거"를 만들어야 한다**

첫 버전을 직접 써 보니 문제는 검색이 아니었습니다. 문서 전체를 돌려주니 AI의 컨텍스트가 금방 차고 토큰 비용이 커졌습니다. 그래서 프로젝트를 "검색 도구"가 아니라 **노트에서 근거를 고르고 압축해 AI에게 건네는 파이프라인**으로 다시 정의했습니다. 감으로 줄이지 않기 위해 응답마다 추정 토큰과 압축 여부를 기록하는 계측을 먼저 넣고, 그 데이터를 보며 응답 형식을 단계적으로 줄였습니다. 핵심 사실·근거·출처만 담은 `memory_packet`을 도입했고, 한 번에 다 담지 못하면 AI가 이어서 요청하도록 했습니다. 마지막에는 기본 응답을 가장 작은 요약 모드로 바꿨습니다.

의미 기반 검색을 붙일 때도 선택지가 있었습니다. Elasticsearch 같은 검색 엔진도 가능했지만, 개인 노트를 다루는 도구가 별도 서버나 외부 API에 의존하면 설치가 어렵고 프라이버시 면에서도 맞지 않는다고 판단했습니다. 그래서 사용자 컴퓨터 안에서만 동작하는 로컬 모델과 로컬 벡터 DB를 골랐습니다. 키워드 검색과 의미 검색을 RRF로 합치고 리랭커로 다시 정렬하는 하이브리드 검색을 구현했습니다. 모델이 없는 사용자도 키워드 검색은 쓸 수 있게 폴백을 두었고, 모델 설치는 `setup` 명령 한 줄로 끝나게 바꿨습니다.

**[실행] 배포하고 나서가 진짜 시작이었다**

배포 직후부터 문제가 이어졌습니다. 배포된 패키지가 실행되지 않았고, 배포 플랫폼에서는 경로가 맞지 않았습니다. 하나씩 고치고 나서 태그만 올리면 테스트부터 배포까지 자동으로 되도록 CI를 정리했습니다.

가장 컸던 문제는 메모리였습니다. 실제로 쓰던 중 서버 메모리가 약 45GB까지 올라갔습니다. 원인을 추적해 보니 "모델이 있는지 확인"하는 함수가 호출될 때마다 모델을 새로 로드하고 있었습니다. 모델 인스턴스를 하나로 캐싱하고 인덱싱을 50개 단위 배치로 나눠 약 1GB로 안정화했습니다.

그런데 이 수정이 새 문제를 만들었습니다. 이제 서버가 시작될 때마다 모델을 올렸고, AI 에이전트는 세션마다 서버를 따로 띄우기 때문에 창을 여러 개 열면 모델 사본이 그만큼 메모리에 상주했습니다. 에이전트를 꺼도 백그라운드 인덱싱이 남아 있었습니다. 이번에는 바로 코드를 고치지 않고 **설계 문서부터 썼습니다**. "시작 시 미리 로드"와 "매번 10초 대기"는 각각 메모리와 응답성을 해친다는 이유로 기각했습니다. 그리고 **필요할 때만 모델을 올리고, 3초 안에 준비되지 않으면 키워드 결과를 먼저 돌려주고, 쓰지 않으면 해제하는** 구조를 택했습니다. 종료 경로도 하나로 모아 에이전트가 사라지면 인덱싱과 워커가 함께 정리되게 했고, 각 동작을 테스트로 고정했습니다.

방법을 통째로 바꾼 적도 있습니다. 코드가 커져서 모노레포로 전환했는데, 배포가 깨지고 DB 라이브러리 버전이 의도치 않게 내려가는 등 문제가 연쇄적으로 생겼습니다. 하나를 고치면 다음 문제가 나오는 상황을 보고, 원인이 개별 버그가 아니라 한 번에 크게 옮긴 방식 자체라고 판단해 롤백했습니다. 이후 큰 변경은 설계 → 계획 → 검증 순서로 작게 나눠 진행합니다.

**[결과] 무엇이 달라졌나**

- AI 에이전트가 제 노트에서 필요한 근거만 출처와 함께 받아 씁니다. 더 필요하면 스스로 이어서 요청합니다.
- 외부 API 키나 별도 서버 없이 `npx` 한 줄로 설치하고, 사용자 컴퓨터 안에서 의미 검색까지 동작합니다.
- 서버 메모리를 약 45GB에서 1GB 수준으로 낮췄고, 이후 의미 검색을 쓰지 않을 때는 모델이 메모리에 올라가지 않게 했습니다.
- 10개월 동안 129개 커밋, 65개 PR, npm v0.3.29까지 혼자 기획·구현·배포·운영했습니다.
- [사용 지표가 있다면: npm 주간 다운로드 N회 / GitHub 스타 N개 / 이슈·피드백 사례]

**[나의 강점] 끝까지 따라가는 집요함, 그리고 틀린 판단을 되돌리는 용기**

이 프로젝트에서 제가 가장 자주 한 일은 "고쳤다고 생각한 것이 정말 고쳐졌는지 다시 의심하는 일"이었습니다. 메모리 문제를 고친 뒤에도 실제 사용 방식(여러 에이전트 세션)에서 다시 확인했고, 그래서 두 번째 문제를 찾았습니다. 모노레포처럼 제가 내린 판단이 틀렸을 때는 고집하지 않고 되돌렸습니다. 마이리얼트립에서도 맡은 일의 범위가 아니라 **문제가 실제로 풀렸는지**를 기준으로, 작은 일부터 끝까지 해내며 범위를 넓혀 가고 싶습니다.

## 6. 제출 전 체크리스트

- [ ] **수치 검증**: "45GB → 1GB"는 커밋 메시지(PR #58) 기록입니다. 측정 환경(Vault 문서 수, OS)을 기억한다면 한 줄 덧붙이면 신뢰도가 올라갑니다. `tests/resume_validation.ts`의 처리량/지연 수치는 *목표값*이라 측정 결과로 쓰면 안 됩니다. 쓰려면 직접 실행해서 나온 값을 쓰세요.
- [ ] **사용자 관점 결과 추가**: npm 다운로드 수, 스타, 외부 사용자 피드백처럼 "다른 사람의 문제가 풀렸다"는 증거가 하나라도 있으면 꼭 넣으세요. 공고가 가장 강조한 "무엇이 해결됐는지"에 해당합니다.
- [ ] **팀 프로젝트가 아니므로** "내 역할"을 따로 쓸 필요는 없습니다. 대신 "기획·설계·구현·배포·운영 전부"를 맡았다는 점이 End-to-End로 읽히게 하세요.
- [ ] **기술 용어 줄이기**: 읽는 사람이 개발자가 아닐 수 있습니다. RRF, Cross-Encoder, AbortController 같은 용어는 초안처럼 "무엇을 위해서"로 바꿔 쓰고, 상세는 GitHub 링크로 넘기세요.
- [ ] **링크 첨부**: GitHub 저장소, npm 페이지, 그리고 근거 문서 2개(`docs/superpowers/specs/2026-07-05-lazy-local-ai-lifecycle-design.md`, `docs/collect-context-guide.md`) 정도를 함께 걸어 두면 "근거 → 실행"을 직접 확인할 수 있습니다.
- [ ] **겸업 관련**: FAQ상 창업 등 다른 일과의 겸업은 원칙적으로 허용되지 않습니다. 오픈소스 개인 프로젝트 유지 여부는 인터뷰에서 질문이 나올 수 있으니 답을 준비해 두세요.
- [ ] **마감**: 지원 마감은 2026년 10월 11일입니다.
