# 성능 측정 결과

이 문서는 저장소에 포함된 계측 도구로 재현 가능한 측정 결과를 기록합니다.

## 측정 환경

| 항목 | 값 |
| --- | --- |
| CPU | 4 vCPU (`nproc` = 4) |
| Node.js | v22.22.2 |
| 대상 Vault | 합성 문서 300건 / 2.9MB / 본문 약 967K자 |
| 로컬 모델 | **미설치** (임베딩·리랭커 없음 → 키워드 폴백 경로) |

> 임베딩/리랭커 모델이 없는 환경이므로 아래 수치는 **키워드 검색 폴백 경로** 기준입니다.
> 하이브리드 검색(벡터 + 리랭킹) 지연시간은 `scripts/benchmark_rerank.ts`로 별도 측정합니다.

## 1. 청킹 워커 풀 — 풀 크기에 따른 처리량

`src/utils/worker/WorkerPool.ts` + `src/utils/worker/chunkingWorker.ts`
문서 300건(총 청크 2,098개)을 청킹하는 데 걸린 시간입니다.

| 풀 크기 | 소요 시간 | docs/sec | 단일 워커 대비 |
| ---: | ---: | ---: | ---: |
| 1 | 11,774ms | 25 | 1.00× |
| 2 | 6,216ms | 48 | 1.89× |
| **4** | **3,854ms** | **78** | **3.06×** |
| 8 | 4,431ms | 68 | 2.66× |

**해석:** 4 vCPU 환경에서 워커 4개가 최적이며, 8개로 늘리면 컨텍스트 스위칭 비용 때문에
오히려 15% 느려집니다. `RAGIndexer`가 `new WorkerPool(4)`를 쓰는 근거가 여기에 있습니다.

## 2. I/O 동시 실행 제한 — 세마포어 유/무

문서 300건을 읽는 데 걸린 시간입니다.

| 방식 | 소요 시간 |
| --- | ---: |
| 무제한 동시 읽기 (`Promise.all`) | 83.7ms |
| 세마포어 상한 10 | **47.3ms** |

**해석:** 동시 실행을 제한한 쪽이 **1.77배 빠릅니다.** 파일 디스크립터를 300개 동시에 여는 것보다
10개로 제한해 순차적으로 처리하는 편이 커널 스케줄링과 캐시 지역성 측면에서 유리합니다.
세마포어는 메모리 보호 장치일 뿐 아니라 처리량 자체를 개선합니다.

동시 실행 상한이 실제로 지켜지는지도 검증했습니다.

| 설정 상한 | 관측된 동시 실행 피크 |
| ---: | ---: |
| 3 | 3 |
| 10 | 10 |

## 3. 도구 호출 지연시간

MCP stdio로 실제 도구 호출 155건을 수행했습니다 (오류 0건).

| 항목 | 값 |
| --- | ---: |
| `initialize` 응답까지 | 447ms |
| 최초 `search` (Vault 300건 전체 로드 + 키워드 인덱싱 포함) | 245ms |

| action / mode | 호출 수 | median | p95 | 평균 응답 크기 |
| --- | ---: | ---: | ---: | ---: |
| `search` / summary | 15 | 1.4ms | 3.0ms | 1,007자 |
| `search` / aggressive | 15 | 3.6ms | 5.6ms | 1,469자 |
| `search` / balanced | 15 | 3.7ms | 5.0ms | 2,032자 |
| `search` / none | 15 | 5.8ms | 7.5ms | 74,390자 |
| `read` / summary | 15 | 1.4ms | 3.2ms | 1,235자 |
| `read` / none | 15 | 1.6ms | 2.4ms | 4,939자 |
| `collect_context` / summary | 8 | 8.4ms | 12.8ms | 3,783자 |
| `collect_context` / none | 8 | 20.2ms | 22.2ms | 76,727자 |

**해석:** `search`를 기본값(`summary`)으로 호출하면 무압축(`none`) 대비 응답이
**74,390자 → 1,007자로 약 74배 줄어듭니다.** 압축 모드는 응답 크기뿐 아니라
지연시간도 함께 낮춥니다(5.8ms → 1.4ms).

## 4. 컨텍스트 압축률

`src/tools/vault/metrics.ts`가 기록한 JSONL 152건을
`scripts/vault-metrics-report.mjs`로 집계한 결과입니다.

| compression mode | 호출 수 | 평균 추정 토큰 | p95 토큰 | 원문 대비 압축률 |
| --- | ---: | ---: | ---: | ---: |
| `summary` (기본값) | 38 | 378 | 1,010 | **92.6%** |
| `aggressive` | 38 | 606 | 1,009 | 88.2% |
| `balanced` | 38 | 984 | 1,652 | 81.7% |
| `none` | 38 | 15,088 | 24,870 | -61.4% |

| action | 호출 수 | 평균 추정 토큰 | 압축률 |
| --- | ---: | ---: | ---: |
| `search` | 60 | 6,260 | 43.9% |
| `read` | 60 | 874 | 25.5% |
| `collect_context` | 32 | 6,875 | -5.5% |

**해석:** 기본 모드에서 원문의 **92.6%를 덜어내고** 평균 378토큰으로 응답합니다.
`none` 모드의 압축률이 음수인 것은 JSON 래핑과 메타데이터가 원문보다 커지기 때문이며,
`collect_context`가 음수인 것도 여러 문서의 근거를 묶어 구조화하는 특성 때문입니다.

## 재현 방법

```bash
# 1. 계측 로그를 남기며 서버 실행 (MCP 클라이언트에서 도구를 호출)
VAULT_DIR_PATH=/path/to/vault \
VAULT_METRICS_LOG_PATH=./metrics/vault.jsonl \
node build/index.js

# 2. 집계 리포트 출력
npm run metrics:report -- ./metrics/vault.jsonl
npm run metrics:report -- ./metrics/vault.jsonl --json

# 3. 하이브리드 검색(벡터 + 리랭킹) 지연시간 — 로컬 모델 설치 필요
npx @sunub/obsidian-mcp-server setup
npm run benchmark:cli-streaming
npx tsx scripts/benchmark_rerank.ts
```

## 알려진 한계

- 위 수치는 로컬 모델이 없는 환경에서 측정되어 **벡터 검색과 리랭킹 경로는 포함하지 않습니다.**
- 합성 문서 기반이므로 실제 Vault의 문서 길이 분포와 다를 수 있습니다.
- 단일 머신 단일 실행 결과이며, 반복 측정에 따른 분산은 기록하지 않았습니다.
