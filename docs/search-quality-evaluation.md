# 검색 품질 평가: 현재 공백과 개선 계획

## 요약

이 프로젝트는 검색이 **빨리 끝났는지**만 측정해 왔고, **정답 문서를 찾았는지**는 한 번도 측정하지 않았다. 게다가 지금까지 외부에 인용한 성능 수치(초당 2.6만 건 인덱싱, 하이브리드 검색 15ms 이내)는 실제 검색 파이프라인의 성능을 나타내지 않는 스크립트에서 나왔다.

따라서 두 가지를 할 수 없는 상태다.

1. 하이브리드 검색과 리랭커가 검색 품질을 **얼마나** 높였는지 말할 수 없다.
2. 속도를 위해 리랭커를 건너뛰는 규칙이 검색 품질을 **떨어뜨렸는지** 판단할 수 없다.

이 문서는 공백의 근거를 정리하고, 이를 메우는 평가 방법과 수치를 인용하는 기준을 정한다.

## 1. 현재 공백

### 1.1 검색 품질 지표가 없다

저장소 어디에도 Recall@k, MRR, nDCG 같은 지표나, 질의마다 정답 문서를 지정한 평가셋(golden set)이 없다.

💡 **Recall@k**: 정답 문서가 상위 k개 결과 안에 들어온 질의의 비율이다.
💡 **MRR (Mean Reciprocal Rank)**: 첫 번째 정답 문서의 순위를 역수로 바꿔 평균 낸 값이다. 정답이 위에 있을수록 1에 가깝다.

유일한 검색 벤치마크인 `scripts/benchmark_rerank.ts`는 리랭커를 건너뛰었을 때 **걸린 시간**만 비교한다. 결과 순위가 어떻게 달라졌는지는 보지 않는다.

### 1.2 품질을 바꿀 수 있는 최적화가 검증 없이 들어가 있다

실제 검색 경로에는 순위에 영향을 주는 규칙이 있다.

| 규칙 | 위치 | 동작 |
|---|---|---|
| 벡터 거리 기준 리랭커 건너뛰기 | `src/utils/VaultManger/VaultManager.ts:285` | 1위 결과의 코사인 거리가 `0.2` 미만이면 리랭킹 없이 벡터 검색 순위를 그대로 반환한다 |
| 벡터 거리 기준 리랭커 건너뛰기 (결합 단계) | `src/utils/VaultManger/VaultManager.ts:192` | 결합한 후보 중 하나라도 청크 거리가 `0.2` 미만이면 결합 결과의 리랭킹을 건너뛴다 |

`scripts/benchmark_rerank.ts:68`의 "제목 일치 Fast-Path"는 벤치마크에만 있고 실제 검색 경로에는 없다.

두 규칙 모두 **속도를 얻는 대신 품질이 떨어질 수 있는** 결정이다. 1위 문서 하나가 가깝다고 해서 2위 이하의 순위까지 맞다는 보장은 없다. 임계값 `0.2`의 근거(주석에는 "유사도 0.80 이상"이라고만 적혀 있다)도 데이터로 검증되지 않았다.

### 1.3 `tests/resume_validation.ts`의 수치는 실제 성능을 재지 않는다

| 인용해 온 수치 | 스크립트가 실제로 하는 일 | 문제 |
|---|---|---|
| 초당 약 2.6만 건 인덱싱 | `FILE_COUNT = 50000`(10행)으로 경로를 만들지만, 실제 파일은 1,000개만 생성한다(36행, 내용은 `"# Test\nContent"` 15바이트). 인덱싱에는 경로 5,000개를 넘긴다(42행). | 존재하지 않는 경로 4,000개에서 `readFile`이 실패하고, `Indexer.processFile`의 catch 블록(`src/utils/Indexer.ts:190`)은 로그만 남기고 넘어간다. **실패한 80%도 처리량에 포함된다.** 외부에 인용한 "10만 건"은 코드 어디에도 없다. |
| 하이브리드 검색 15ms 이내 | `indexer.search("Test")`를 1회 호출한다(51행). | 키워드 역색인만 쓴다. 임베딩, 벡터 검색, RRF 결합, 리랭커가 모두 빠져 있어 **하이브리드 검색이 아니다.** 측정도 한 번뿐이라 분포(p50, p95)가 없다. |
| 경로 탈출 차단 100% | 스크립트 안에서 `path.resolve` + `startsWith`로 검사를 새로 구현하고(71행) 3가지 경로만 확인한다. | 실제 코드(`VaultManager.ts:633`, `relative` 기반 검사)를 호출하지 않는다. 스크립트 쪽 `startsWith` 방식은 `/Users/user/vault-evil` 같은 형제 경로를 통과시킨다. **실제 코드가 아니라 더 약한 복사본을 검증하고 있다.** 실제 코드는 `tests/unit/VaultManagerWriteBoundary.test.ts`가 따로 검증하고 있었다(4절 참고). |

### 1.4 왜 중요한가

- 검색 품질은 이 프로젝트의 핵심 가치다. ADR 0001이 정의한 Agent Context Pipeline은 올바른 근거를 골라 에이전트에게 넘기는 것이 목적이다. 잘못된 문서를 빠르게 넘기는 것은 개선이 아니다.
- 품질을 재지 않으면 검색 방식, 임베딩 모델, 청킹 방식, 리랭커 임계값을 **감으로** 바꾸게 되고, 성능이 떨어져도 알아챌 수 없다.
- 근거가 약한 수치를 인용하면 나머지 설계 결정까지 신뢰를 잃는다.

## 2. 개선 계획

### 2.1 평가셋 만들기

실제 Vault에서 질의 30~50개를 만들고 질의마다 정답 문서를 지정한다. 한 가지 유형에 몰리지 않도록 아래 유형을 섞는다.

| 유형 | 예시 | 무엇을 확인하나 |
|---|---|---|
| `exact_title` | 문서 제목 그대로 | 제목 Fast-Path가 정답을 1위로 올리는지 |
| `keyword` | 고유명사, 라이브러리 이름, 에러 메시지 | 키워드 검색(BM25/역색인)이 필요한 경우 |
| `semantic` | 문서에 없는 표현으로 바꾼 질문 | 벡터 검색이 필요한 경우 |
| `multi_doc` | 정답이 여러 문서에 흩어진 질문 | Recall@k가 의미 있는 경우 |
| `link` | 백링크를 따라가야 찾을 수 있는 질문 | Backlink 인덱스의 기여 |
| `no_answer` | Vault에 답이 없는 질문 | 억지로 결과를 내는지(선택) |

저장 위치는 `eval/search/queries.jsonl`로 한다. Vault 내용이 들어가므로 공개 저장소에는 올리지 않는다(`.gitignore`에 추가). 형식은 다음과 같다.

```json
{"id": "q001", "type": "keyword", "query": "LanceDB 인덱스 재생성 오류", "relevant": ["dev/lancedb-troubleshooting.md"], "note": "에러 메시지 원문 검색"}
{"id": "q002", "type": "semantic", "query": "로컬 모델이 느릴 때 먼저 확인할 것", "relevant": ["ai/local-llm-latency.md", "ai/llama-cpp-settings.md"]}
```

- `relevant`는 Vault 기준 상대 경로이고, 문서 단위로 채점한다. 청크 단위 채점은 청킹 방식이 바뀔 때마다 정답이 무너지므로 처음에는 쓰지 않는다.
- 질의는 검색 결과를 보기 **전에** 작성한다. 결과를 보고 질의를 고치면 평가셋이 현재 구현에 맞춰진다.

### 2.2 구성별 비교

같은 평가셋으로 아래 구성을 모두 돌린다. 이 비교가 "무엇이 품질을 올렸고 무엇이 떨어뜨렸는지"를 보여 준다.

| 구성 | 목적 |
|---|---|
| A. 키워드만 | 기준선 |
| B. 벡터만 (Dense) | 기준선 |
| C. 키워드 + 벡터 (RRF) | 하이브리드 결합의 효과 |
| D. C + 리랭커 (항상 실행) | 리랭커의 효과 |
| E. D + 거리 `< 0.2` 건너뛰기 | **현재 동작.** D와의 차이가 곧 건너뛰기 규칙의 품질 비용이다 |
| F. E + 제목 Fast-Path | Fast-Path의 품질 비용 |

E와 D의 품질 차이가 무시할 만하면 건너뛰기 규칙은 검증된 최적화가 된다. 차이가 크면 임계값을 조정하거나(0.1, 0.15, 0.2, 0.25 등으로 스윕) 규칙을 없앤다.

### 2.3 지표

**품질 지표** (질의 유형별로도 나눠 본다)
- Recall@5, Recall@10
- MRR@10
- 문서가 1개인 질의에서의 Hit@1

**지연 지표** (실제 Vault, 전체 파이프라인 기준)
- p50, p95 지연(ms). 워밍업 후 질의당 여러 번 측정한다.
- 모델 로딩 전(cold)과 후(warm)를 구분한다.
- 리랭커 실행 비율: 건너뛰기 규칙이 실제로 얼마나 자주 작동하는지 기록한다.

**인덱싱 지표**
- 실제 Vault의 문서 수, 총 용량, 전체 인덱싱 시간, 초당 문서 수
- **실패한 파일 수를 따로 집계하고 처리량에서 뺀다.**
- 합성 데이터로 규모를 늘려 측정할 때는 실제 파일을 모두 생성하고, 문서 크기 분포를 실제 Vault와 비슷하게 맞춘다.

### 2.4 산출물

- `scripts/eval/search-quality.ts`: 평가셋을 읽고 구성별 지표를 계산한다. (구현 완료, 4절)
- 결과는 `eval/search/results/<날짜>.json`과 사람이 읽는 요약 `eval/search/results/<날짜>.md`로 남긴다. 요약에는 실행 환경(기기, 모델, Vault 규모)을 함께 적는다.
- `tests/resume_validation.ts`는 삭제하고, 인덱싱과 지연 측정은 위 기준을 따르는 `scripts/eval/indexing-benchmark.ts`로 대체한다. (구현 완료, 삭제는 아직)
- 경로 탈출 검증은 벤치마크가 아니라 `VaultManager`의 실제 검사 함수를 호출하는 단위 테스트로 옮긴다. 형제 경로(`vault-evil`), `..` 조합, 심볼릭 링크 경우를 포함한다.

## 3. 수치 인용 기준

평가가 끝나기 전까지 아래 기준을 따른다.

| 수치 | 상태 | 기준 |
|---|---|---|
| 초당 2.6만 건 인덱싱 / 10만 건 | ❌ 인용 중단 | 실제 파일, 실패 건수 제외 기준으로 다시 측정한 뒤 새 수치를 쓴다 |
| 하이브리드 검색 15ms 이내 | ❌ 인용 중단 | 전체 파이프라인의 p50과 p95로 다시 측정한다 |
| "높은 검색 정확도" | ❌ 근거 없음 | Recall@5와 MRR로 대체한다 |
| 경로 탈출 차단 100% | ❌ 인용 중단 | 실제 코드에 대한 단위 테스트 통과로 대체한다 |
| npm·Smithery 배포, 누적 사용자 수 | ✅ 사용 가능 | — |

평가가 끝나면 다음과 같이 **비교 가능한 형태**로 인용한다.

> 키워드·벡터 하이브리드 검색과 로컬 리랭커를 도입해, 직접 만든 질의 [N]개 평가셋에서 Recall@5를 [a](벡터만)에서 [b]로, MRR@10을 [c]에서 [d]로 개선했다. 속도를 위한 리랭커 건너뛰기 규칙은 Recall@5 손실 [e]%p 안에서 p95 지연을 [f]ms에서 [g]ms로 줄이는 것을 확인한 뒤 유지했다.

## 4. 측정 결과 (2026-09-27, 수정 전)

재현 방법: 실제 Vault의 Markdown 391개를 복사한 Vault에서 측정했다(원본 Vault의 벡터 캐시는 건드리지 않았다). 환경은 Apple Silicon 18코어, 48GB, Node 24, 임베딩 `Xenova/paraphrase-multilingual-MiniLM-L12-v2`, 리랭커 `Xenova/bge-reranker-base`이다. 원자료는 `eval/*/results/`에 있다(개인 Vault 내용이 들어가므로 커밋하지 않음).

```bash
npx tsc && npx tsc-alias
npx tsx scripts/eval/indexing-benchmark.ts --vault <복사본> --synthetic 10000 --rag
npx tsx scripts/eval/search-quality.ts --vault <복사본> --rerank-cache eval/search/results/rerank-cache.json
npx tsx scripts/eval/report.ts eval/search/results/search-<시각>.json eval/indexing/results/*.json
```

### 4.1 검색 품질 (질의 42개, 결과 10개)

| 구성 | Recall@5 | Recall@10 | MRR@10 | 실제 경로 지연 |
|---|---:|---:|---:|---:|
| A. 키워드만 | **0.665** | **0.778** | **0.595** | 1ms 미만 |
| B. 벡터만 (현재 코드) | 0.127 | 0.183 | 0.117 | p50 45ms |
| B'. 벡터만, 질의 접두사 제거 | 0.480 | 0.603 | 0.370 | p50 48ms |
| C. 하이브리드, 리랭커 없음 | 0.645 | 0.760 | 0.528 | p50 54ms |
| D. 하이브리드 + 리랭커 항상 | 0.516 | 0.587 | 0.381 | 수 초~20초 |
| **E. 현재 동작 (임계값 0.2)** | 0.516 | 0.587 | 0.381 | **p50 5.9초, p95 7.6초** |

- 재현 코드(E)와 실제 `VaultManager.hybridSearch`의 결과는 42개 질의 모두 순위까지 일치했다.
- 모델이 내려간 뒤 첫 검색(cold)은 p50 5.8초였고, 키워드 검색으로만 대체된 경우는 없었다.
- 리랭커 구성의 지연은 측정 중 다른 프로세스(Ollama)가 CPU를 함께 쓴 구간이 있어 흔들렸다(D: 12~19초). 실제 경로 지연은 그 프로세스가 끝난 뒤 측정한 값이다.

### 4.2 해석

1. **현재 검색은 키워드 검색만 쓸 때보다 나쁘다.** 현재 동작(E)은 키워드만(A)보다 MRR@10이 0.214 낮다(95% CI [-0.389, -0.040]). 지연은 1ms 미만에서 약 6초로 늘었다.
2. **벡터 검색이 거의 작동하지 않는 원인은 접두사다.** `search_query: ` / `search_document: `는 nomic 계열 임베딩 모델의 규칙인데, 이 프로젝트의 모델(paraphrase-multilingual-MiniLM)은 이 규칙으로 학습되지 않았다. 질의 쪽 접두사만 빼도 Recall@5가 0.127에서 0.480으로 오른다(CI [+0.218, +0.496]). 문서 쪽 접두사까지 빼고 다시 인덱싱한 결과는 아직 측정하지 않았다.
3. **ANN 인덱스(IVF-PQ)는 원인이 아니다.** 인덱스를 우회한 정확 검색과 결과가 같다.
4. **리랭커는 품질을 올리지 않고 떨어뜨리는 쪽이다.** C에서 D로 가면 Recall@5가 0.129 떨어진다(CI [-0.300, +0.038], 질의 42개로는 유의하지 않음). 키워드로만 찾은 문서는 매칭된 청크가 없어서, 리랭커가 본문 대신 `frontmatter.summary`나 파일 경로를 채점하는 것이 유력한 원인이다(`VaultManager.ts:205`).
5. **건너뛰기 임계값 0.2는 사실상 작동하지 않는다.** 결합 단계 리랭커가 42개 질의 모두에서 실행됐다. 임계값을 올리면 리랭커를 덜 실행하고 품질이 C에 가까워진다(0.3: Recall@5 0.635, 실행률 60% / 0.4: 0.621, 12%).

### 4.3 인덱싱

| 항목 | 결과 |
|---|---|
| 키워드 인덱스, 실제 Vault 391개(4.6MB) | 중앙값 0.53초, **초당 약 740건**, 실패 0건 |
| 키워드 인덱스, 실제 문서 내용으로 만든 파일 1만 개(118MB) | 중앙값 10.2초, **초당 약 980건**, 실패 0건 |
| 임베딩 인덱스, 빈 캐시에서 생성 | 11분(662초), 청크 5,834개(초당 8.8개). 내용이 있는 문서 372개 100% 반영(빈 파일 19개는 청크 없음) |

- 기존에 인용한 "초당 2.6만 건"은 실제 처리량보다 약 27배 크다.
- `경험정리/포트폴리오.md` 한 파일(1MB, 이미지가 base64로 들어 있음)이 청크 2,404개로 전체의 41%를 차지한다. 인덱싱 시간과 저장 공간 대부분이 의미 없는 텍스트에 쓰인다. → 4.7에서 수정.
- 모델 준비가 3초 안에 끝나지 않으면 그 파일의 임베딩을 조용히 건너뛰는 경로가 있다(`RAGIndexer.buildFileRecords` → `withEmbedder(3000)`). 이번 측정에서는 1회차에 모두 반영되어 문제가 드러나지 않았다.

### 4.4 경로 경계

실제 `writeRawDocument` 기준: `../` 상위 경로, 형제 디렉터리(`vault-evil`), Vault 밖 절대 경로는 모두 차단된다(형제 경로 단위 테스트 추가). **Vault 안의 심볼릭 링크가 밖을 가리키면 그 링크를 거쳐 Vault 밖에 파일이 써진다.** 경로 검사가 `resolve`/`relative`의 문자열 비교라 심볼릭 링크를 따라가지 않기 때문이다. 쓰기 전에 `realpath`로 실제 경로를 확인해야 한다.

### 4.5 수정과 재측정 (2026-09-28)

4.2의 진단에 따라 세 가지를 고쳤다.

1. **임베딩 접두사 제거:** `VaultManager.safeSemanticSearch`와 `RAGIndexer`에서 `search_query: ` / `search_document: `를 뺐다. 기존 인덱스를 다시 만들도록 `INDEX_VERSION`을 7로 올렸다.
2. **리랭커 제거:** 접두사를 고친 인덱스에서 리랭커 후보를 같은 평가셋으로 비교한 뒤 결정했다.

   | 후보 | Recall@5 | Recall@10 | MRR@10 | 지연 p50 |
   |---|---:|---:|---:|---:|
   | **리랭커 없음 (채택)** | 0.752 | 0.815 | **0.672** | **16ms** |
   | 기존 리랭커 (두 단계, 입력 그대로) | 0.714 | 0.806 | 0.579 | 5.4초 |
   | 결합 단계만, 입력을 본문으로 수정 | 0.621 | 0.792 | 0.545 | 1.7초 |
   | 두 단계, 입력을 본문으로 수정 | 0.754 | 0.841 | 0.625 | 6.1초 |

   리랭커를 넣은 어떤 구성도 리랭커가 없는 구성보다 MRR@10이 높지 않았고, 지연은 100배 이상 늘었다. 질의 42개로는 품질 차이가 유의하지 않으므로, "같거나 나은 품질을 훨씬 적은 비용으로"를 근거로 리랭커를 뺐다. 한국어 문서가 많은 Vault에서 `bge-reranker-base`가 잘 맞지 않는 것으로 보이며, 다국어 리랭커를 다시 검토할 때 같은 평가셋으로 비교한다.
3. **심볼릭 링크 우회 차단:** 쓰기 전에 이미 존재하는 가장 깊은 상위 경로의 `realpath`가 Vault 안인지 확인한다. 대상이 없는 링크(dangling)도 거부한다. 회귀 테스트 3개를 추가했다(Vault 밖 링크, 대상 없는 링크, Vault 안 링크 허용).

**실제 검색 경로(`VaultManager.hybridSearch`)의 수정 전후** (같은 질의 42개, 짝지은 부트스트랩 95% 신뢰구간)

| Recall@10 | 0.587 | **0.815** | +0.228 [+0.093, +0.371] |

### 4.8 청킹 기준 비교 (2026-11-10)

**질문:** 현재 청커(`RecursiveCharacterTextSplitter`, 500/50토큰, 길이는 GPT 토크나이저 cl100k로 셈)의 기준이 임베딩 모델에 맞는가.

**사전 확인 (임베딩 없이 청크만 나눈 통계):**

- cl100k 기준 "500토큰" 청크는 임베딩 모델 토크나이저 기준으로 중앙값 296토큰이다. 한국어에서 cl100k가 토큰을 더 많이 세므로 의도보다 작게 잘린다.
- 섹션 문맥(`Section:`, `Outline:`)을 붙이면 102개가 모델 토큰 500을 넘어 `RAGIndexer`에서 뒷부분이 잘린 채 임베딩된다.
- 모델 토크나이저 기준 500으로 자르면 문맥을 붙인 뒤 390개가 500을 넘는다. 크기는 문맥을 붙일 여유를 두고 정해야 한다.
- 임베딩 모델(paraphrase-multilingual-MiniLM)은 sentence-transformers 설정상 최대 128토큰으로 학습된 것으로 알려져 있다(위치 임베딩은 512).

**방법:** 실험용 청커(`scripts/eval/lib/chunking-variants.ts`)를 `indexing-benchmark --chunker`로 끼워 넣어 production 코드는 바꾸지 않았다. cl100k 500/50 재귀 분할 구성이 현재 워커와 같은 청크 3,615개를 만드는 것을 확인했다. 구성마다 빈 캐시부터 색인하고 질의 42개로 평가했다. ANN 인덱스(IVF-PQ)를 만들 때마다 결과가 흔들리므로 핵심 구성은 3회 색인해 평균을 냈다. 원자료는 `eval/search/results/chunking/`에 있다.

```bash
npx tsx scripts/eval/indexing-benchmark.ts --vault <복사본> --rag --runs 1 --strip-prefix --chunker model:256:32:recursive
npx tsx scripts/eval/search-quality.ts --vault <복사본> --strip-prefix --only B_dense,E_production
```

| 구성 (토큰 기준:크기:겹침:경계) | 청크 | 첫 색인 | 하이브리드 R@5 | 하이브리드 MRR@10 | 벡터만 R@5 | 벡터만 MRR@10 |
|---|---:|---:|---:|---:|---:|---:|
| **현재** cl100k:500:50:재귀 (3회) | 3,615 | 93초 | 0.770 | 0.664 (0.652~0.677) | 0.440 | 0.325 |
| model:500:50:재귀 (1회) | 2,462 | 88초 | 0.708 | 0.665 | 0.433 | 0.341 |
| **model:256:32:재귀 (3회)** | 5,159 | 100초 | 0.804 | 0.701 (0.686~0.714) | 0.587 | 0.456 |
| model:128:16:재귀 (3회) | 12,066 | 136초 | 0.831 | 0.718 (0.709~0.725) | 0.583 | 0.456 |
| model:256:32:제목 (3회) | 6,238 | 103초 | 0.829 | 0.679 (0.667~0.704) | 0.573 | 0.436 |

현재 구성 대비 차이 (3회 평균을 질의별로 짝지은 부트스트랩 95% CI):

| 구성 | 하이브리드 ΔR@5 | 하이브리드 ΔMRR@10 | 벡터만 ΔMRR@10 |
|---|---|---|---|
| model:256:32:재귀 | +0.034 [-0.060, +0.131] | +0.037 [-0.051, +0.130] | **+0.131 [+0.025, +0.242]** |
| model:128:16:재귀 | **+0.062 [+0.002, +0.131]** | +0.054 [-0.044, +0.160] | **+0.131 [+0.013, +0.258]** |

**해석:**

1. **청크를 모델 토큰 256 이하로 줄이면 벡터 검색이 좋아진다.** 벡터만 MRR이 0.325에서 0.456으로 오르고 세 구성 모두 유의하다. 청크가 모델의 학습 길이보다 길어 mean pooling으로 의미가 흐려진다는 가설과 맞는다. 반대로 키운 구성(model:500)은 벡터·하이브리드 모두 나아지지 않았다.
2. **하이브리드 검색도 같은 방향으로 오르지만 질의 42개로는 대부분 유의하지 않다.** 3회 범위로 보면 256과 128의 하이브리드 MRR은 현재 구성의 범위와 겹치지 않는다.
3. **제목 기준 분할은 추가 이득이 없다.** 같은 256에서 청크만 20% 늘고 MRR은 재귀 분할보다 낮다. 짧은 섹션이 32토큰 미만 청크로 많이 생기는 것(119개, 재귀는 26개)이 원인으로 보인다.
4. **128은 256보다 약간 낫지만 비용이 크다.** 청크 2.3배, 색인 시간 +36%다. 비용 대비로는 model:256:32:재귀가 가장 낫다(청크 +43%, 색인 시간 +7%).
5. 질의 유형별로 보면 256에서 키워드·다중 문서 질의는 오르고 의미 질의(semantic) MRR은 내려갔다(0.667 → 0.587, 1회차 기준). 의미 질의 12개는 따로 확인할 필요가 있다.

**권고:** 청크 길이를 임베딩 모델 토크나이저로 세고 크기를 256/32로 바꾼다.

**반영 (INDEX_VERSION 9):**

- 청킹 로직을 `src/utils/worker/chunkDocument.ts`로 분리하고(길이 함수를 주입받아 테스트 가능), 워커가 임베딩 모델 토크나이저로 길이를 잰다. 모델 파일이 없으면 GPT 토크나이저로 대신 잰다.
- 임베딩 모델 토크나이저는 워커당 약 357MB를 쓴다(GPT 토크나이저는 약 111MB). 워커 4개를 그대로 두면 색인 중 메모리가 크게 늘어나므로 청킹 워커를 1개로 줄였다. 색인 시간은 임베딩이 대부분이라 영향이 없었다.

실제 워커 경로(`--chunker` 없이)로 같은 사본을 다시 색인해 확인했다. 원자료는 `eval/search/results/chunking/production-v9/`, `previous-v8/`에 있다.

|---|---:|---:|
| 청크 수 | 3,615 | 5,159 |
| 첫 색인 시간 | 97~98초 (2회) | 97~103초 (3회) |
| 색인 프로세스 최대 메모리 | 3.0~4.1GB (2회) | **2.6GB** (3회) |
| 하이브리드 MRR@10 | 0.664 (3회 평균, 4.8) | **0.704** (0.700~0.706) |

청크 수는 43% 늘었지만 청크가 짧아져 색인 시간은 같고, 최대 메모리는 줄었다. 품질 수치는 실험(4.8)의 model:256:32:재귀 결과와 일치한다.

### 4.10 ANN 검색 폭(nprobes) 조정 (2026-11-18)

**문제:** 4.7, 4.8에서 같은 청크 구성을 다시 색인할 때마다 하이브리드 MRR@10이 흔들렸다. 원인을 분리하려고 임베딩과 청크는 고정하고 **벡터 인덱스(IVF-PQ)만 5회 재생성**해 정확 검색(`bypassVectorIndex`)과 비교했다(`scripts/eval/ann-variance.ts`). 청크 5,161개, 질의 42개.

| 지표 | ANN (`nprobes` 20, 5회) | 정확 검색 (5회) |
|---|---|---|
| 벡터 MRR@10 | 0.451 (0.438~0.457) | 0.457 (전부 동일) |
| 하이브리드 MRR@10 | 0.728 (0.711~0.753, 표준편차 0.017) | 0.726 (전부 동일) |
| 정확 검색 상위 30개 청크 중 ANN에도 있는 비율 | 0.916 | 1.000 |

- 정확 검색은 재생성과 무관하게 같았고(대조군), ANN만 달라졌다. 흔들림의 원인은 인덱스 학습(k-means 파티션 배치)이다.
- ANN 평균과 정확 검색의 차이는 신뢰구간이 0을 포함한다(하이브리드 +0.003 [-0.019, 0.030]). ANN이 체계적으로 나쁜 것이 아니라 불안정한 것이다.
- 원인은 `nprobes(20)`이 파티션 71개 중 28%만 봐서 경계의 이웃을 놓치는 것이다. 놓치는 청크가 재생성마다 달라진다.

**검색 폭 스윕 (`scripts/eval/ann-sweep.ts`, 인덱스 5회 재생성):**

| nprobes | refineFactor | 청크 겹침 | 하이브리드 MRR 표준편차 | 지연 p50 |
|---:|---:|---:|---:|---:|
| 20 (이전) | 1 | 0.920 | 0.008 | 9.4ms |
| 40 | 1 | 0.989 | 0.007 | 9.7ms |
| 71 (전체) | 1 | 1.000 | 0.000 | 10.1ms |
| 71 | 5 / 10 | 1.000 | 0.000 | 14.2 / 17.0ms |

- `refineFactor`는 1, 5, 10에서 겹침과 MRR이 같고 지연만 늘었다. 손실의 원인이 PQ 압축이 아니라 IVF 파티션 누락이라는 뜻이다. 1을 유지한다.
- 정확 검색(지연 p50 15.1ms)보다 전체 파티션 검색(10.1ms)이 빠르다.

**수정 (`VectorDB.search`):** `nprobes`를 20에서 파티션 수(`floor(√행 수)`, 인덱스 생성과 같은 공식)로 바꿨다. 파티션 수를 넘는 `nprobes`는 오류 없이 전체와 같게 처리되는 것을 확인했다(LanceDB 0.27.2). 인덱스 구조와 청크는 바뀌지 않으므로 `INDEX_VERSION`은 올리지 않는다.

**수정 후 확인 (운영 경로 `vectorDB.search`, 인덱스 5회 재생성):**

- 벡터 MRR@10 0.457, 하이브리드 MRR@10 0.726으로 정확 검색과 같고 재생성 간 표준편차는 0이다.
- 청크 겹침은 4회 1.000, 1회 0.999이고, 정확 검색과 상위 10개 문서 목록이 다른 질의는 0개다.
- 질의 지연은 p50 10.2ms에서 10.7ms로 +0.5ms다. `countRows()` 호출은 0.09ms다.

**이 수정이 하지 않는 것:** 평균 검색 품질을 올리지는 않는다(하이브리드 평균 0.724에서 0.726). 얻는 것은 정확 검색과 같은 결과와 재생성 간 안정성이다. 이후 하이브리드 지표 비교를 3회 평균 없이 한 번의 색인으로 읽을 수 있다.

**한계:**

- 5,161개 규모에서만 확인했다. 전체 파티션을 훑는 것은 행 수에 비례해 느려지므로 규모가 커지면 비율을 낮춰야 한다. 이 데이터에서 겹침 0.99에는 파티션의 약 56~63%가 필요했다.
- 질의 42개, vault 하나다. 지연에는 질의 임베딩 시간이 포함되지 않는다.
- 재생성이 인덱스를 교체하는지(쌓이지 않는지)는 테이블 버전과 인덱스 개수로 확인했다. 재생성마다 이전 버전 파일이 남아 벡터 캐시가 커진다(62MB에서 90MB).

**보정 방식 검증 (`scripts/eval/ann-calibration.ts`, 운영 코드에는 미반영):** 규모에 따라 `nprobes`를 자동으로 정하려면 저장된 청크로 재현율을 재서 목표를 넘는 최소값을 고르는 방식을 생각할 수 있다. 질의를 무엇으로 만드느냐가 결과를 좌우했다.

| 보정 질의 | 최근접 거리 평균 (평가셋 0.346) | 목표 0.99에서 평가셋 겹침 | 판정 |
|---|---:|---:|---|
| 청크 벡터 그대로 | 0.159 | 0.960 | 실패 (낙관적 편향) |
| 섹션 제목, 없으면 TF-IDF 상위 4단어 (`mixed`) | 0.324 | 0.991 | 통과 |

- 청크 벡터는 같은 문서의 이웃 청크가 가까이 있어 쉬운 문제가 된다. 질의 분포를 평가셋에 맞추면 곡선 차이가 ±0.005 안으로 줄었다.
- 0.999 목표는 선택된 `nprobes`의 범위(16)가 사전 기준(10)을 넘어 실패했다. 선택된 값에서 평가셋 겹침은 0.998 이상이었다.
- 한계: vault 하나, 평가셋 42개, 평가셋 곡선의 독립 측정은 재생성 3회다. 다른 vault와 큰 규모에서의 유지 여부는 확인하지 못했다.
