| **[문서 Rn]** | 공식 문서, 모델 카드, 기업 기술 블로그 | 중간~높음. 저자가 자기 제품을 설명하는 경우가 있다 |

## 1. 면접 질문에 대한 답변

### 1.1 "dense search가 없으면 RAG가 아닌가요?"

**30초 답변**

> 아닙니다. RAG는 "외부 지식을 검색해서 생성 모델의 입력에 넣는다"는 구조를 가리키고, 검색 방식은 정해져 있지 않습니다. RAG라는 이름을 만든 Lewis et al.(2020) 논문은 dense retriever를 썼지만, 이후 In-Context RALM(Ram et al., 2023)은 BM25만으로도 언어 모델 성능이 크게 오른다는 것을 보였습니다. 실제로 BEIR 벤치마크에서는 BM25가 여러 dense 모델보다 일반화를 잘했고, 그래서 요즘은 BM25와 dense를 같이 쓰는 하이브리드가 흔합니다. 제 프로젝트도 로컬 모델이 없으면 키워드 검색만으로 동작하고, 모델이 있으면 두 결과를 RRF로 합칩니다.

**2분 답변으로 늘릴 때 덧붙일 내용**

1. **정의의 출처.** Lewis et al.(2020)은 RAG를 사전학습된 생성 모델(parametric memory)과 "검색으로 접근하는 외부 지식"(non-parametric memory)을 결합한 모델로 정의했다. 그 논문에서 외부 지식은 위키피디아의 dense vector index였다. 즉 **dense는 원 논문의 구현 선택이지 정의의 조건이 아니다.** [논문 R1]
2. **sparse 검색만으로도 효과가 있다는 근거.** In-Context RALM은 모델 구조를 바꾸지 않고 검색한 문서를 프롬프트 앞에 붙이기만 했는데, 기성 BM25 검색기를 쓴 345M GPT-2가 762M GPT-2보다 나았다. [논문 R5]
3. **dense가 항상 낫지 않다는 근거.** BEIR(18개 데이터셋, zero-shot)에서 BM25는 견고한 기준선이었고 dense 모델은 학습 분포 밖에서 BM25보다 크게 떨어지는 경우가 있었다. [논문 R7] 2025년 Google DeepMind 연구(ICLR 2026)는 단일 벡터 임베딩의 **차원 수가 표현할 수 있는 top-k 조합을 이론적으로 제한한다**는 것을 보였고, 이를 시험하는 LIMIT 데이터셋에서 최신 임베딩 모델은 고전했지만 BM25는 거의 만점이었다. [논문 R8]
4. **에이전트 시대의 흐름.** Anthropic은 Claude Code가 미리 만든 인덱스 대신 `glob`, `grep` 같은 도구로 필요한 순간에 파일을 찾는(just-in-time) 방식을 쓰고, 처음부터 넣는 컨텍스트(CLAUDE.md)와 섞는 하이브리드라고 설명한다. 대신 실행 중 탐색은 미리 계산된 결과를 꺼내는 것보다 느리다고 적었다. [문서 R20] → "검색 = 벡터 DB"라는 등식은 업계에서도 이미 깨져 있다.
5. **내 프로젝트의 근거.** 같은 질의 42개에서 키워드 검색만 쓴 구성이 Recall@5 0.665였고, 버그가 있던 당시 벡터 검색만 쓴 구성은 0.127이었다. 하이브리드가 의미 있으려면 두 검색기가 각자 제대로 동작해야 한다는 것을 측정으로 확인했다. [실측 4.1]

**함정: "그럼 dense는 필요 없나요?"라는 반문에 대비한다.**

> 그렇지는 않습니다. 둘은 실패하는 질의가 다릅니다. BM25는 질의와 문서가 같은 단어를 써야 찾고, dense는 표현이 달라도 의미가 비슷하면 찾지만 고유명사나 에러 코드처럼 정확히 일치해야 하는 질의에 약합니다. 제 평가셋에서도 벡터 검색의 접두사 버그를 고친 뒤 하이브리드 검색의 의미 질의(semantic) 유형 MRR@10이 0.207에서 0.667로, 질의 유형 중 가장 많이 올랐습니다. 벡터 검색이 제대로 동작해야 찾을 수 있는 질의가 따로 있다는 뜻입니다. 그래서 둘 중 하나를 고르기보다 합치는 쪽을 택했습니다. [실측 4.5]

### 1.2 "청킹 전략은 무엇을 사용했나요?"

**30초 답변**

> 마크다운 구분자 우선의 재귀 분할(recursive character splitting)을 쓰고, 청크 길이는 **임베딩 모델의 토크나이저로 세서** 256토큰, 겹침 32토큰으로 자릅니다. 각 청크에는 섹션 제목과 문서 개요를 짧게 붙여 임베딩합니다. 처음에는 GPT 토크나이저 기준 500토큰이었는데, 임베딩 모델이 128토큰으로 학습됐다는 걸 확인하고 크기별로 비교 실험을 했습니다. 256으로 줄였을 때 벡터 검색 MRR@10이 0.325에서 0.456으로 유의하게 올랐고, 128은 조금 더 좋았지만 청크가 2.3배로 늘어서 256을 골랐습니다. 제목 기준 분할도 시험했는데 추가 이득이 없었습니다.

**2분 답변으로 늘릴 때 덧붙일 내용**

1. **"전략" = 경계 + 크기 + 겹침 + 문맥 보강.** 면접관이 묻는 것은 보통 이 네 가지다. 하나씩 답한다.
   - 경계: `RecursiveCharacterTextSplitter`가 문단(`\n\n`) → 줄(`\n`) → 공백 → 글자 순으로 자르기를 시도한다. [코드 `src/shared/indexing/worker/chunkDocument.ts:52`]
   - 크기/겹침: 256/32, 임베딩 모델 토큰 기준. [코드 `chunkDocument.ts:17-18`]
   - 문맥 보강: `Section: <섹션 제목>`, `Outline: <H1/H2 3개>`를 본문 앞에 붙여 임베딩한다. [코드 `chunkDocument.ts:84`, `RAGIndexer.ts:95-100`]
   - 전처리: base64 이미지(data URI)를 청킹 전에 제거한다. [코드 `chunkDocument.ts:69`]
2. **왜 크기를 바꿨나.** 청크를 "몇 토큰"으로 셀지는 **청크를 소비하는 모델의 토크나이저**로 정해야 한다. GPT의 cl100k 토크나이저로 500을 세면 이 임베딩 모델 토크나이저로는 중앙값 296토큰이었고, 모델은 128토큰으로 학습됐다. 학습 길이보다 긴 입력은 mean pooling에서 의미가 흐려진다는 가설을 세우고 측정했다. [실측 4.8, 문서 R14]
3. **연구 결과와 일치한다.** 2025년 Fraunhofer 연구는 최적 청크 크기가 데이터셋과 임베딩 모델에 따라 다르며, 짧은 사실형 답에는 64~128토큰, 넓은 문맥이 필요한 답에는 512~1024토큰이 낫다고 보고했다. [논문 R12] 개인 노트 Vault는 짧은 사실형 질의가 많아서 작은 쪽이 유리했던 것으로 해석한다. [해석]
4. **왜 의미 기반(semantic) 청킹을 안 썼나.** Vectara 연구(NAACL 2025 Findings)는 semantic chunking의 계산 비용이 일관된 성능 향상으로 정당화되지 않는다고 결론냈다. [논문 R11] 2026년 8월 연구도 8개 청킹 전략을 비교해 "비싼 방법은 단순한 방법보다 일관되게 낫지 않고, 최적 전략은 임베딩 모델·데이터셋·지표에 따라 다르다"고 보고했다. [논문 R13] 그래서 단순한 방법을 기본값으로 두고 측정으로 크기만 조정했다.

**함정: "청크가 문맥을 잃는 문제는 어떻게 했나요?"**

> 청크 앞에 섹션 제목과 문서 개요를 붙이는 방식으로 일부 보완했습니다. Anthropic의 Contextual Retrieval과 같은 방향인데, 그쪽은 LLM으로 청크마다 문맥 설명을 생성해서 붙이고, 저는 비용 때문에 제목 구조만 씁니다. 다만 문맥을 붙이면 임베딩 입력이 길어지므로, 청크 크기를 정할 때 문맥이 들어갈 여유를 남겨야 했습니다. 500토큰 기준으로 자르면 문맥을 붙인 뒤 390개 청크가 입력 한도를 넘어 잘렸습니다. [문서 R16, 실측 4.8]

## 2. RAG의 기초

### 2.1 정의

**RAG(Retrieval-Augmented Generation)**: 생성 모델이 답을 만들기 전에 외부 지식 저장소에서 관련 자료를 **검색**해 입력에 **보강(augment)** 하는 방식이다. [논문 R1]

Lewis et al.은 두 종류의 기억을 구분했다. [논문 R1]

| 구분 | 무엇 | 장점 | 단점 |
|---|---|---|---|
| parametric memory | 모델 가중치에 저장된 지식 | 빠르다, 추론에 녹아 있다 | 갱신하려면 재학습, 출처를 댈 수 없다, 환각 |
| non-parametric memory | 검색으로 꺼내는 외부 문서 | 문서만 바꾸면 갱신, 출처 제시 가능 | 검색이 틀리면 답도 틀린다 |

💡 **같은 시기의 REALM**(Guu et al., 2020)은 검색기를 사전학습 단계부터 함께 학습했다. RAG는 사전학습된 검색기와 생성기를 결합해 미세조정했다. [논문 R2]

### 2.2 파이프라인 구성 요소

```
[색인 단계, 오프라인]
문서 → 파싱 → 정제 → 청킹 → (임베딩) → 색인 저장

[질의 단계, 온라인]
질의 → 검색(sparse/dense/hybrid) → 결합 → (리랭킹) → 선택/압축 → 프롬프트 → 생성
```

이 프로젝트에서 각 단계가 어디에 있는지는 7.1절에 정리했다.

### 2.3 RAG의 발전 단계

Gao et al.의 서베이는 RAG를 세 단계로 나눈다. [논문 R3]

| 단계 | 특징 | 예 |
|---|---|---|
| Naive RAG | 색인 → 검색 → 생성의 고정된 한 번 흐름 | top-k 청크를 그대로 붙임 |
| Advanced RAG | 검색 전후 최적화 | 질의 재작성, 하이브리드 검색, 리랭킹, 압축 |
| Modular RAG | 모듈을 바꾸고 조합 | 라우팅, 반복 검색, 메모리 |

2025년 이후에는 에이전트가 **언제, 무엇을, 몇 번** 검색할지 스스로 정하는 **Agentic RAG**가 별도 분야로 정리됐다. [논문 R4, 문서 R20]

**이 프로젝트는 어디에 있나:** 하이브리드 검색과 RRF를 쓰므로 Advanced RAG에 해당하고, 검색 결과를 에이전트용 컨텍스트로 선택·압축하는 단계까지 RAG의 범위로 본다(ADR 0001). [코드 `docs/adr/0001-agent-context-pipeline-over-search-backend.md`]

### 2.4 RAG가 해결하지 못하는 것

- **검색이 틀리면 생성도 틀린다.** 그래서 이 프로젝트는 생성 품질보다 검색 품질(Recall, MRR)을 먼저 측정했다. [실측]
- **찾아도 모델이 안 쓸 수 있다.** 긴 입력의 중간에 있는 정보를 모델이 덜 활용한다는 "Lost in the Middle" 결과가 있다. [논문 R18] → 많이 넣는 것보다 정확한 몇 개를 넣는 것이 중요하다.
- **긴 컨텍스트 모델이 있으면 RAG가 필요 없나?** 연구 결과는 "둘을 같이 쓸 때 가장 낫다" 쪽이다. 4K 컨텍스트 + 검색이 16K 컨텍스트 모델과 비슷한 성능을 내고, 긴 컨텍스트 모델에도 검색을 더하면 더 좋아졌다는 결과가 있다. [논문 R19] 비용과 지연도 문서 전체를 넣는 것보다 낮다. [해석]

## 3. 검색의 기초: sparse와 dense

### 3.1 검색 방식의 분류

| 분류 | 표현 | 대표 | 강점 | 약점 |
|---|---|---|---|---|
| **sparse (어휘 기반)** | 어휘 크기만큼 긴 벡터, 대부분 0 | TF-IDF, **BM25** | 정확한 단어·고유명사·코드 일치, 학습 불필요, 빠름, 설명 가능 | 동의어·다른 표현을 못 찾음 (vocabulary mismatch) |
| **dense (의미 기반)** | 수백 차원의 실수 벡터 | DPR, Sentence-BERT, E5 | 표현이 달라도 의미가 같으면 찾음 | 학습 분포 밖에서 약함, 정확한 일치에 약함, 모델이 필요 |
| **learned sparse** | 모델이 단어 가중치와 확장어를 학습 | SPLADE | 역색인 그대로 쓰면서 의미 확장 | 모델 필요 |
| **late interaction** | 토큰마다 벡터, 토큰 단위로 비교 | ColBERT | 품질 높음 | 저장 공간이 큼 |

[논문 R6, R7, R9, R10]

💡 "sparse = 키워드 검색"으로만 외우면 SPLADE 질문에서 막힌다. sparse는 **벡터 모양**(대부분 0)을 가리키는 말이다.

### 3.2 역색인 (inverted index)

책 뒤의 "찾아보기"와 같다. `단어 → 그 단어가 나오는 문서 목록`을 미리 만들어 두고, 질의의 단어로 목록을 바로 꺼낸다. 모든 문서를 훑지 않아도 된다.

```
"lancedb" → {a.md, c.md}
"청킹"    → {b.md, c.md}
```

이 프로젝트의 `Indexer`가 이 구조다. [코드 `src/shared/indexing/Indexer.ts:16`]

### 3.3 TF-IDF에서 BM25로

문서 점수는 "질의 단어가 이 문서에 얼마나 중요한가"의 합이다. 중요도는 두 가지로 정한다.

- **TF (term frequency)**: 이 문서에 그 단어가 몇 번 나오나. 많을수록 관련이 높다.
- **IDF (inverse document frequency)**: 그 단어가 전체 문서 중 몇 개에 나오나. 드물수록 변별력이 높다. "the", "것"은 낮고 "LanceDB"는 높다.

TF-IDF는 둘을 곱한다. 문제는 두 가지다.

1. 단어가 100번 나온 문서가 10번 나온 문서보다 10배 관련 있지는 않다. → **TF 포화(saturation)** 가 필요하다.
2. 긴 문서는 그냥 길어서 단어가 많이 나온다. → **문서 길이 정규화**가 필요하다.

**BM25**(Okapi BM25)는 확률적 관련성 모델(Probabilistic Relevance Framework)에서 나온 점수 함수로, 이 두 문제를 매개변수로 다룬다. [논문 R6]

$$
\text{score}(D, Q) = \sum_{q \in Q} \text{IDF}(q) \cdot \frac{f(q, D) \cdot (k_1 + 1)}{f(q, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}
$$

| 기호 | 뜻 |
|---|---|
| $f(q, D)$ | 문서 D에서 단어 q가 나온 횟수 (TF) |
| $\|D\|$, avgdl | 문서 D의 길이, 전체 문서 평균 길이 |
| $k_1$ | TF가 얼마나 빨리 포화되는지. 0이면 TF를 무시(나왔나/안 나왔나만 봄), 클수록 TF를 많이 반영 |
| $b$ | 길이 정규화 강도. 0이면 길이 무시, 1이면 완전히 정규화 |
| IDF | Lucene 구현은 $\ln\left(1 + \frac{N - n(q) + 0.5}{n(q) + 0.5}\right)$. N은 전체 문서 수, n(q)는 q가 나온 문서 수 |

Lucene(Elasticsearch, OpenSearch의 기반)의 기본값은 $k_1 = 1.2$, $b = 0.75$이다. [문서 R15]

**직관으로 외우기:** 분수 부분은 TF가 커질수록 $(k_1+1)$에 가까워지며 더 이상 커지지 않는다(포화). 문서가 평균보다 길면 분모가 커져 점수가 깎인다(길이 정규화).

### 3.4 이 프로젝트의 키워드 검색은 BM25인가?

**아니다.** 정확히 말하면 **IDF 가중 불리언 매칭**이다. [코드 `src/shared/indexing/Indexer.ts:77-164`]

| 항목 | BM25 | 이 프로젝트 `Indexer.search` |
|---|---|---|
| TF | 포화 함수로 반영 | **반영 안 함.** 역색인이 `Set<filePath>`라 횟수를 저장하지 않는다 (`Indexer.ts:16`) |
| 길이 정규화 | $b$로 반영 | **없음** |
| IDF | $\ln(1 + \frac{N-n+0.5}{n+0.5})$ | $\ln(N/df) + 1$ (`Indexer.ts:123`) |
| 최소 일치 | 없음(엔진 옵션) | 질의 토큰 수에 따른 minimum-should-match (`Indexer.ts:147`) |
| 색인 단위 | 보통 문서 또는 필드 | 문서 단위. 본문 + 제목 + 태그 + 파일명 + 링크를 한 집합에 넣는다 |

💡 **면접에서 쓸 수 있는 연결:** BM25에서 $k_1 = 0$으로 두면 분수 부분이 "나왔으면 1, 아니면 0"이 된다. 즉 이 프로젝트의 점수는 **$k_1 = 0$인 BM25의 극단(IDF 공식만 다름)** 과 같은 구조다. 이렇게 설명하면 "BM25를 모른다"가 아니라 "BM25의 어느 부분을 생략했고 그 대가가 무엇인지 안다"가 된다. [해석, 수식에서 직접 유도]

**토큰화의 한계도 함께 알고 있어야 한다.** [코드]

- 문서는 `/[a-z0-9가-힣]+/g`로 자르고 (`Indexer.ts:262`), 질의는 공백으로 자른다 (`Indexer.ts:83`). 2026-11-10 전까지는 이 차이 때문에 `LanceDB,`(앞뒤 문장부호)나 `tailwind-merge`, `Next.js`(중간 문장부호)가 본문의 `lancedb`, `tailwind`+`merge`와 맞지 않았다.
- 지금은 질의 토큰마다 ① 원형 ② 앞뒤 문장부호를 뗀 형태 ③ 중간 문장부호로 나뉜 조각이 모두 들어 있는 문서 중 하나라도 맞으면 일치로 본다(`Indexer.ts:96-130`). 원형을 남긴 이유는 태그(`c++`)와 파일명(`my-note`)이 문장부호째 색인되기 때문이다. 한 글자 조각(`I/O`의 `i`, `o`)은 거의 모든 문서에 있어 잡음이 되므로 뺐다.
- 결과: 질의 42개에서 현재 동작의 Recall@5 0.752 → 0.800, MRR@10 0.650 → 0.711. 하이픈이 든 라이브러리 이름 질의 3개가 1위로 올라왔고 악화된 질의는 없었다. 다만 신뢰구간 하한이 0이라 유의하다고 단정할 수 없고, 한 글자 조각 규칙은 평가셋을 보고 넣은 것이라 새 질의로 다시 확인해야 한다. [코드, 실측 4.9]
- 💡 **면접 포인트:** "색인할 때와 질의할 때 같은 분석기(analyzer)를 써야 한다"는 검색 엔진의 기본 원칙이다. Elasticsearch도 필드의 analyzer를 질의에 그대로 적용하는 것이 기본 동작이다. 이 버그는 그 원칙을 어긴 사례였다.
- 한국어는 조사가 붙은 어절 단위로 색인된다. 문서의 "검색을"과 질의의 "검색"은 다른 토큰이다. Elasticsearch는 이 문제를 Nori 같은 형태소 분석기로 풀고, 다국어 검색 연구에서도 한국어 BM25에 Nori를 쓴다. [논문 R17] 다만 형태소 분석기별 한국어 검색 성능을 통제된 조건에서 비교한 공개 연구는 찾지 못했다. **직접 평가셋으로 재야 한다.** [해석]

그럼에도 이 단순한 키워드 검색이 질의 42개에서 Recall@5 0.665였다. 개인 노트에서는 제목·태그·고유명사로 찾는 질의가 많기 때문으로 해석한다. [실측 4.1, 해석]

### 3.5 dense 검색: bi-encoder와 임베딩

**bi-encoder**: 질의와 문서를 **따로** 같은 모델에 넣어 벡터로 만들고, 두 벡터의 코사인 유사도로 비교한다. 문서 벡터를 미리 계산해 둘 수 있어 빠르다. DPR이 질의응답용 dense 검색에서 BM25를 이긴 대표 사례다. [논문 R9] 문장 단위 임베딩 학습은 Sentence-BERT가 대표적이다. [논문 R10]

**이 프로젝트의 임베딩 모델** [코드 `src/shared/local-ai/Embedder.ts:13`, `:74-75`]

| 항목 | 값 | 근거 |
|---|---|---|
| 모델 | `Xenova/paraphrase-multilingual-MiniLM-L12-v2` (sentence-transformers 모델의 ONNX 변환) | [코드] |
| 차원 | 384 | [코드 `VectorDB.ts:15`] |
| 학습 방식 | 영어 모델을 교사로 한 지식 증류로 50개 이상 언어에 확장 | [논문 R10b, 문서 R14] |
| 최대 시퀀스 길이 | 128토큰 (sentence-transformers 설정) | [문서 R14] |
| 풀링 | mean pooling + L2 정규화 | [코드] |

💡 **mean pooling**: 토큰 벡터들의 평균을 문장 벡터로 쓴다. 입력이 길어질수록 많은 토큰이 평균에 섞여 특정 내용의 신호가 약해진다. 4.8절 실험의 가설이 이것이다. [해석, 실측으로 일부 지지]

💡 **질의/문서 접두사(prefix)**: E5, nomic-embed 같은 모델은 `query: ` / `search_query: `처럼 접두사를 붙이도록 학습됐다. 이 접두사를 **그렇게 학습되지 않은 모델**에 붙이면 오히려 품질이 떨어진다. 이 프로젝트가 실제로 이 버그를 겪었다(7.3절). 모델을 바꿀 때는 모델 카드의 사용법을 반드시 확인한다. [실측 4.2]

### 3.6 ANN 인덱스: IVF-PQ

벡터가 많으면 모든 벡터와 비교(정확 검색)하는 대신 **근사 최근접 이웃(ANN)** 을 쓴다.

- **IVF (inverted file)**: 벡터를 k-means로 여러 파티션에 나누고, 질의와 가까운 파티션 몇 개(`nprobes`)만 본다.
- **PQ (product quantization)**: 벡터를 여러 조각으로 나눠 조각마다 코드북 번호로 압축한다. 메모리가 줄고 거리 계산이 빨라지지만 근사 오차가 생긴다.

이 프로젝트: 행이 256개 이상이면 `numPartitions = √N`, `numSubVectors = 96`, cosine으로 IVF-PQ를 만들고, 검색 시 `nprobes = 20`. [코드 `VectorDB.ts:216-229`, `:371`]

**알아 둘 함정:** IVF는 k-means 결과에 따라 파티션이 달라져서 **색인을 다시 만들 때마다 검색 결과가 조금씩 흔들린다.** 이 프로젝트에서 같은 청크 구성을 세 번 다시 색인했을 때 하이브리드 MRR@10이 0.652~0.677로 흔들렸다. 그래서 청킹 비교 실험은 3회 평균으로 판단했다. 또 정확 검색과 비교해 ANN이 벡터 검색 부진의 원인이 아님도 확인했다. [실측 4.2, 4.7, 4.8]

### 3.7 dense만으로는 안 되는 이론적 이유 (2025)

Weller et al.(ICLR 2026)은 단일 벡터 임베딩의 차원 d가 "어떤 문서 조합이 top-k로 나올 수 있는지"를 제한한다는 것을 보였다. "Jon은 사과를 좋아한다" 같은 단순한 문서로 만든 LIMIT 데이터셋에서 최신 임베딩 모델은 낮은 점수를 받았고, 어휘 차원이 매우 큰 BM25는 거의 만점이었다. [논문 R8]

**1.1 질문과의 연결:** "dense가 RAG의 본질"이라는 주장은 이론적으로도 성립하지 않는다. dense는 강력한 **도구 하나**다.

## 4. 결합: 하이브리드 검색, RRF, 리랭킹

### 4.1 왜 점수가 아니라 순위로 합치나

BM25 점수(0~수십, 상한 없음)와 코사인 유사도(-1~1)는 단위가 다르다. 그대로 더하면 한쪽이 지배한다. 정규화(min-max 등)를 해도 질의마다 분포가 달라 불안정하다.

**RRF (Reciprocal Rank Fusion)** 는 점수를 버리고 **순위만** 쓴다. [논문 R11b]

$$
\text{RRF}(d) = \sum_{r \in \text{검색기들}} \frac{1}{k + \text{rank}_r(d)}
$$

- 여러 검색기에서 모두 상위에 있는 문서가 올라온다.
- $k$가 크면 순위 간 차이가 줄어 하위 문서도 기여하고, 작으면 1위가 지배한다.
- $k = 60$이 사실상 표준값이다. Elasticsearch의 RRF `rank_constant` 기본값도 60이다. [문서 R15b] (원 논문이 k를 어떻게 정했는지는 PDF 본문 추출에 실패해 직접 확인하지 못했다.)
- Cormack et al.(SIGIR 2009)은 이 단순한 방법이 Condorcet 결합이나 개별 학습 순위 방법보다 낫다고 보고했다. [논문 R11b]

### 4.2 이 프로젝트의 하이브리드 검색

[코드 `src/shared/vault-manager/VaultManager.ts:97-215`]

```
질의
 ├─ 키워드 검색 (Indexer.search) ──── 문서 단위 순위
 └─ 벡터 검색 (LanceDB, limit×3개 청크) ─ 청크 단위 순위
        └─ 같은 문서의 청크 중 가장 높은 순위만 문서 순위로 사용
 → RRF (k=60)로 문서 단위 결합 → 상위 limit개
```

| 설계 결정 | 이유 | 대가 |
|---|---|---|
| 모델이 없으면 키워드 검색만 반환 (`:103`) | 설치 직후나 모델 로딩 실패에도 검색이 동작해야 한다 | 의미 검색이 빠진다는 안내 메시지를 함께 반환한다 |
| 문서 단위로 결합 | 키워드 색인이 문서 단위라 단위를 맞춰야 한다 | 키워드로만 찾은 문서에는 "어느 부분이 맞았는지"(matched chunk)가 없다 |
| 리랭커를 쓰지 않음 (`:192`) | 4.3절 | |

### 4.3 리랭킹 (cross-encoder)

**cross-encoder**는 질의와 문서를 **한 입력으로 같이** 넣어 관련도 점수 하나를 낸다. 두 텍스트의 토큰이 서로를 보면서 계산되므로 bi-encoder보다 정확하지만, 문서 벡터를 미리 계산할 수 없어 후보마다 모델을 돌려야 한다. 그래서 보통 "빠른 검색으로 후보 수십 개 → cross-encoder로 재정렬"의 2단계로 쓴다. BEIR에서도 리랭킹 모델이 zero-shot 평균 점수가 가장 높았지만 계산 비용이 컸다. [논문 R7] Anthropic의 실험에서도 리랭킹을 더하면 검색 실패율이 더 줄었다. [문서 R16]

**그런데 이 프로젝트는 리랭커를 뺐다.** 일반론과 반대되는 결정이라 면접에서 꼭 설명할 수 있어야 한다. [실측 4.5]

| 구성 | Recall@5 | MRR@10 | 지연 p50 |
|---|---:|---:|---:|
| **리랭커 없음 (채택)** | 0.752 | **0.672** | **16ms** |
| 기존 리랭커 (두 단계) | 0.714 | 0.579 | 5.4초 |
| 두 단계, 입력을 본문으로 수정 | 0.754 | 0.625 | 6.1초 |

> 리랭커가 일반적으로는 품질을 올리지만, 제가 쓰던 `bge-reranker-base`는 한국어 노트가 많은 제 Vault에서 어떤 구성으로도 MRR을 올리지 못했고 지연은 100배 이상 늘었습니다. 질의 42개로는 품질 차이가 유의하지 않아서, "같거나 나은 품질을 훨씬 적은 비용으로"를 근거로 뺐습니다. 다국어 리랭커가 나오면 같은 평가셋으로 다시 비교할 계획입니다.

**배운 점:** "논문에서 좋다고 했다"는 내 데이터에서 좋다는 뜻이 아니다. 언어, 문서 종류, 모델 조합에 따라 다르다. **그래서 평가셋이 먼저다.** [해석]

## 5. 청킹

### 5.1 왜 자르나

1. **임베딩 모델의 입력 한도.** 이 모델은 128토큰으로 학습됐다. 문서 전체를 넣을 수 없다. [문서 R14]
2. **검색 정밀도.** 문서 하나에 주제가 여러 개면 벡터 하나가 모든 주제의 평균이 되어 어느 질의와도 애매하게 가깝다. [해석, 3.5 mean pooling]
3. **생성 모델의 컨텍스트 예산.** 관련 부분만 넣어야 비용이 줄고 "Lost in the Middle" 문제가 줄어든다. [논문 R18]

반대로 너무 작게 자르면 청크 하나에 답을 이해할 문맥이 부족해지고, 청크 수가 늘어 색인 비용이 커진다. **크기는 정밀도와 문맥 사이의 균형이다.**

### 5.2 청킹 전략의 분류

| 전략 | 방법 | 장점 | 단점 | 근거 |
|---|---|---|---|---|
| 고정 크기 | N토큰마다 자름 | 단순, 빠름 | 문장·문단 중간에서 잘림 | |
| **재귀 분할** | 큰 구분자(문단)부터 시도해 크기에 맞을 때까지 작은 구분자로 내려감 | 단순하면서 구조를 어느 정도 지킴 | 의미 경계를 보장하지 않음 | 이 프로젝트 |
| 구조 기반 | 마크다운 제목, HTML 태그 기준 | 저자가 정한 경계 | 섹션 길이가 들쑥날쑥 | 이 프로젝트에서 비교 |
| 의미 기반 (semantic) | 인접 문장 임베딩 유사도가 떨어지는 곳에서 자름 | 주제 경계 | 모든 문장을 임베딩해야 함, 이득이 일관되지 않음 | [논문 R11, R13] |
| 명제 단위 (proposition) | LLM으로 원자적 사실 문장으로 다시 씀 | 검색 단위가 정밀 | LLM 비용 | [논문 R21] |
| 계층 / parent-child | 작은 청크로 검색하고 큰 부모 청크를 반환 | 정밀도와 문맥을 모두 | 저장 구조가 복잡 | |
| RAPTOR | 청크를 군집화·요약해 트리를 만들고 여러 층에서 검색 | 여러 문서에 걸친 질문 | 요약 비용 | [논문 R22] |
| **late chunking** | 문서 전체를 긴 컨텍스트 임베딩 모델에 넣은 **뒤** 토큰 벡터를 청크별로 풀링 | 청크 벡터가 문서 문맥을 담음, 추가 학습 불필요 | 긴 컨텍스트 + mean pooling 모델 필요 | [논문 R23] |
| **contextual retrieval** | LLM으로 청크마다 "이 청크가 문서에서 어떤 위치인지" 설명을 생성해 붙인 뒤 임베딩과 BM25 색인 | 문맥 손실을 직접 보완 | 청크마다 LLM 호출 (캐싱으로 절감) | [문서 R16] |

**Contextual Retrieval의 수치(자주 잘못 인용됨):** 상위 20개 청크 검색 실패율이 5.7%에서 contextual embedding으로 3.7%(-35%), contextual BM25를 더해 2.9%(-49%), 리랭킹까지 더해 1.9%(-67%)가 됐다. **-67%는 누적 효과**이지 리랭킹 단독 효과가 아니다. 그리고 이 결과도 **embedding + BM25 하이브리드**다. 1.1 질문의 또 다른 근거가 된다. [문서 R16]

### 5.3 최근 연구가 말하는 것 (2024~2026)

| 연구 | 결론 |
|---|---|
| Qu et al., Vectara (2024, NAACL 2025 Findings) | semantic chunking의 계산 비용은 일관된 성능 향상으로 정당화되지 않는다 [논문 R11] |
| Bhat et al., Fraunhofer (2025) | 최적 청크 크기는 데이터셋과 임베딩 모델에 따라 다르다. 짧은 사실형 답은 64~128토큰, 넓은 문맥은 512~1024토큰 [논문 R12] |
| Caspari et al. (2026.08) | 8개 전략 × 2개 코퍼스 × 3개 임베딩 모델. 비싼 방법은 일관된 이득이 드물고, 비슷한 품질의 방법도 색인 처리량·지연·메모리 비용이 크게 다르다. 단순한 방법이 강한 기본값이며 비싼 방법은 **목표 지표에서 측정된 이득**으로 정당화해야 한다 [논문 R13] |

**요약:** "청킹에 정답 전략은 없고, 단순한 방법을 기본으로 두고 내 데이터와 내 임베딩 모델로 측정해 정한다." 이 프로젝트가 한 일이 정확히 이것이다.

### 5.4 이 프로젝트의 청킹

**현재 구현** [코드 `src/shared/indexing/worker/chunkDocument.ts`]

1. `MatterParser`로 frontmatter와 본문을 분리한다.
2. 본문에서 base64 data URI를 지운다(`stripEmbeddedData`). 이미지 대체 텍스트는 남긴다.
3. H1~H3 제목의 위치를 기록한다.
4. `RecursiveCharacterTextSplitter`로 256/32 토큰 단위로 자른다. 토큰은 **임베딩 모델 토크나이저**로 센다(모델 파일이 없으면 GPT 토크나이저로 대신 센다. 이때는 어차피 임베딩을 하지 않는다).
5. 청크마다 속한 섹션 제목과 문서 개요(H1/H2 최대 3개)를 `context`로 붙인다.
6. 임베딩 직전에 `context + 본문`이 500토큰을 넘으면 뒤를 자른다(`RAGIndexer.ts:103`).
7. 청크 ID는 `<파일 경로>_chunk_<순번>`, 제목·태그·날짜·요약 등 메타데이터를 함께 저장한다.

**변경 이력과 근거** [실측 4.7, 4.8]

| 시점 | 변경 | 근거 |
|---|---|---|
| 초기 | GPT(cl100k) 토큰 기준 500/50 | 근거 없음. 흔한 기본값 |
| 2026-11-10 | base64 data URI 제거 | 한 파일이 이미지 때문에 청크 2,404개(전체의 40%)를 차지. 제거 후 청크 -39.8%, 첫 색인 170초 → 99초, 품질 차이는 유의하지 않음 |
| 2026-11-10 (미커밋) | 임베딩 모델 토큰 기준 256/32 | 아래 표 |

| 구성 (토큰 기준:크기:겹침:경계) | 청크 수 | 첫 색인 | 하이브리드 MRR@10 | 벡터만 MRR@10 |
|---|---:|---:|---:|---:|
| 기존 cl100k:500:50:재귀 | 3,615 | 93초 | 0.664 | 0.325 |
| model:500:50:재귀 | 2,462 | 88초 | 0.665 | 0.341 |
| **model:256:32:재귀 (채택)** | 5,159 | 100초 | 0.701 | **0.456** |
| model:128:16:재귀 | 12,066 | 136초 | 0.718 | 0.456 |
| model:256:32:제목 기준 | 6,238 | 103초 | 0.679 | 0.436 |

- 벡터만 MRR@10의 향상(+0.131)은 95% 신뢰구간이 0을 포함하지 않아 유의하다. 하이브리드의 향상은 질의 42개로는 대부분 유의하지 않다.
- 128은 256보다 조금 낫지만 청크 2.3배, 색인 시간 +36%. 비용 대비 256을 골랐다.
- 제목 기준 분할은 짧은 섹션이 32토큰 미만 청크로 많이 생겨(119개, 재귀는 26개) 오히려 낮았다.
- **아직 확인할 것:** 의미 질의(semantic) 유형은 256에서 MRR이 0.667 → 0.587로 내려갔다(1회차). 12개 질의를 따로 봐야 한다.

## 6. 평가

### 6.1 검색 지표

| 지표 | 정의 | 언제 보나 |
|---|---|---|
| **Recall@k** | 정답 문서 중 상위 k개 안에 들어온 비율 | 생성 모델에 k개를 넘길 때 "필요한 자료가 들어갔나" |
| **Hit@1** | 1위가 정답인 질의의 비율 | 결과를 하나만 쓸 때 |
| **MRR@k** | 첫 정답 순위의 역수 평균 (1위면 1, 2위면 0.5) | 정답이 얼마나 위에 있나 |
| **nDCG@k** | 순위가 낮을수록 할인하고, 관련도 등급(0/1/2…)을 반영 | 관련도가 여러 단계일 때. BEIR의 기본 지표 [논문 R7] |

이 프로젝트는 문서 단위 이진 정답이라 Recall@k와 MRR@k를 주 지표로 썼다. 청크 단위로 채점하지 않은 이유는 청킹 방식이 바뀔 때마다 정답이 무너지기 때문이다. [실측 2.1]

### 6.2 생성 지표

검색이 맞아도 답이 틀릴 수 있다. RAGAS는 정답 없이 LLM으로 faithfulness(답이 검색 문맥에 근거하나), answer relevance, context relevance를 재는 프레임워크다. [논문 R24] 이 프로젝트는 아직 생성 단계 평가를 하지 않았다. → 9절 꼬리 질문 대비.

### 6.3 이 프로젝트의 평가 방법에서 배울 점

1. **질의를 결과를 보기 전에 작성했다.** 결과를 보고 질의를 고치면 평가셋이 현재 구현에 맞춰진다.
2. **유형을 섞었다.** 제목, 키워드, 의미, 다중 문서, 링크, 답 없음. 유형별로 나눠 봐야 "의미 질의는 나빠졌다" 같은 것이 보인다.
3. **짝지은 부트스트랩 95% 신뢰구간**을 냈다. 같은 질의에 대한 두 구성의 차이를 재표본추출해 구간을 만든다. 질의 42개는 작아서 차이가 커 보여도 유의하지 않은 경우가 많았다. **면접에서는 "유의하지 않았다"를 숨기지 않고 말하는 것이 신뢰를 준다.**
4. **재현 코드가 실제 경로와 같은 결과를 내는지 확인했다.** 42개 질의 모두 순위까지 일치. 벤치마크가 실제 코드와 다른 것을 재는 실수(이전 `resume_validation.ts`)를 반복하지 않기 위해서다.
5. **한계:** 한 사람이 만든 평가셋이라 정답 목록에 빠진 문서가 있을 수 있다. 그래서 절대값보다 구성 간 비교를 더 믿는다.

[실측 1~4절]

### 7.1 파이프라인 지도

| 단계 | 파일 | 핵심 |
|---|---|---|
| 파일 탐색·감시 | `src/shared/indexing/DirectoryWalker.ts`, `VaultWatcher.ts` | |
| 키워드 색인 | `src/shared/indexing/Indexer.ts` | 문서 단위 역색인, IDF 가중 불리언 매칭, 백링크 색인 |
| 청킹 | `src/shared/indexing/worker/chunkDocument.ts`, `chunkingWorker.ts` | 워커 스레드에서 실행 |
| 전처리 | `src/shared/markdown/MatterParser.ts`, `stripEmbeddedData.ts` | frontmatter 분리, base64 제거 |
| 임베딩·저장 | `src/shared/indexing/RAGIndexer.ts`, `Embedder.ts`, `VectorDB.ts` | 로컬 ONNX 모델, LanceDB, IVF-PQ |
| 하이브리드 검색 | `src/shared/vault-manager/VaultManager.ts:97` | RRF k=60, 리랭커 없음, 모델 없으면 키워드만 |
| 평가 | `scripts/eval/search-quality.ts`, `indexing-benchmark.ts`, `lib/metrics.ts`, `lib/chunking-variants.ts` | |

### 7.2 개선 이야기 (STAR 형식으로 말하기)

**상황.** 하이브리드 검색과 리랭커를 붙였고 "하이브리드 검색 15ms", "초당 2.6만 건 인덱싱" 같은 수치를 쓰고 있었다.

**문제 발견.** 그 수치를 만든 스크립트를 다시 읽어 보니, 15ms는 키워드 검색 한 번만 잰 값이었고, 처리량은 존재하지 않는 파일 80%의 실패까지 포함한 값이었다. 무엇보다 **검색이 정답을 찾는지는 한 번도 잰 적이 없었다.** [실측 1절]

**행동과 결과.**

| 단계 | 한 일 | 결과 |
|---|---|---|
| ① 평가셋 | 실제 Vault에서 질의 42개, 6개 유형, 정답 문서 지정. A~F 구성 비교 | 현재 동작(E)이 **키워드만 쓸 때보다 나쁘다**는 것을 발견 (MRR@10 0.381 vs 0.595), 지연은 약 6초 |
| ② 원인 1: 접두사 | nomic 계열 접두사(`search_query: `)를 그렇게 학습되지 않은 모델에 붙이고 있었다 | 질의 쪽만 빼도 벡터 Recall@5 0.127 → 0.480 |
| ③ 원인 2: 리랭커 | 키워드로만 찾은 문서는 청크가 없어 리랭커가 본문 대신 요약·경로를 채점. 입력을 고쳐도 리랭커 없는 구성보다 MRR이 높지 않음 | 리랭커 제거 |
| ④ 수정 후 실제 경로 | | Recall@5 0.516 → **0.752**, MRR@10 0.381 → **0.672**, warm p50 5.9초 → **16ms**, cold 5.8초 → 605ms. 모두 95% CI가 0을 포함하지 않음 |
| ⑤ 청킹 정제 | base64 이미지 제거 | 청크 -40%, 첫 색인 -42%, 품질 유지 |
| ⑥ 청크 크기 | 임베딩 모델 토크나이저 기준 256/32 | 벡터만 MRR@10 0.325 → 0.456 (유의) |
| ⑦ 질의 토큰화 | 본문 색인과 질의의 토큰화 규칙을 맞춤(앞뒤·중간 문장부호 처리, 한 글자 조각 제외) | 현재 동작 Recall@5 0.752 → 0.800, MRR@10 0.650 → 0.711. 하이픈이 든 라이브러리 이름 질의 3개가 1위로, 악화 0개 (CI 하한 0이라 유의하다고 단정할 수 없음) |

**교훈.** "좋다고 알려진 부품을 붙이는 것"과 "검색이 좋아지는 것"은 다르다. 측정하지 않으면 개선인지 악화인지 알 수 없다. 실제로 리랭커와 접두사는 둘 다 일반적으로 권장되는 기법이었지만 이 환경에서는 품질을 떨어뜨렸다. [실측, 해석]

### 7.3 인용 가능한 수치와 인용하면 안 되는 수치

`docs/search-quality-evaluation.md` 4.6절을 그대로 따른다. "높은 검색 정확도" 같은 표현은 쓰지 않고 Recall@5와 MRR로 말한다.

## 9. 꼬리 질문 사다리

각 질문에 1~2문장으로 답할 수 있으면 통과다. 화살표는 면접관이 이어서 물을 가능성이 높은 질문이다.

### 9.1 RAG 정의 줄기

1. **RAG란?** → 검색한 외부 지식을 생성 모델 입력에 보강하는 구조. parametric + non-parametric memory. [R1]
2. → **dense 없이도 RAG인가?** → 예. 1.1절.
3. → **그럼 왜 dense를 쓰나?** → vocabulary mismatch. 표현이 다른 질의를 찾는다. 내 평가에서는 벡터 검색 버그를 고친 뒤 의미 질의 MRR이 가장 크게 올랐다.
4. → **BM25와 dense가 각각 실패하는 예는?** → BM25: "로컬 모델이 느릴 때"로 "llama.cpp 설정" 문서 찾기. dense: 에러 코드, 라이브러리 이름, LIMIT 같은 조합 질의. [R8]
5. → **둘을 어떻게 합쳤나?** → RRF, k=60. 점수 단위가 달라 순위로 합침. 4.1절.
6. → **RRF의 k는 무엇을 조절하나?** → 상위 순위의 지배력. 작으면 1위 중심, 크면 평평.
7. → **가중치를 주고 싶으면?** → 검색기별 가중 RRF, 또는 점수 정규화 후 가중합(convex combination). 정규화 방식에 민감하다.

### 9.2 BM25 줄기

1. **BM25를 설명해 보세요.** → TF 포화 + 길이 정규화 + IDF. 수식의 $k_1$, $b$ 의미. 3.3절.
2. → **TF-IDF와 차이는?** → 포화와 길이 정규화.
3. → **당신 구현은 BM25인가?** → 아니다. IDF 가중 불리언 매칭, $k_1 = 0$인 BM25와 같은 구조. 3.4절.
4. → **그런데 왜 잘 됐나?** → 개인 노트는 짧고, 제목·태그·고유명사 질의가 많다. TF의 이득이 작은 환경. [해석]
5. → **한국어 BM25의 문제는?** → 교착어. 어절 단위 색인은 조사 때문에 일치 실패. 형태소 분석(Nori 등)이나 n-gram.
6. → **SPLADE는?** → 모델이 단어 가중치와 확장어를 학습한 sparse 벡터. 역색인 그대로 의미 확장. [R9 계열]

### 9.3 청킹 줄기

1. **청킹 전략은?** → 1.2절.
2. → **크기를 어떻게 정했나?** → 임베딩 모델 토크나이저 기준, 128/256/500 비교, 3회 색인 평균, 부트스트랩 CI.
3. → **왜 토크나이저가 중요한가?** → 같은 "500토큰"도 cl100k와 모델 토크나이저에서 길이가 다르다. 한국어에서 차이가 크다.
4. → **겹침(overlap)은 왜?** → 경계에서 잘린 문장이 양쪽 청크에 남아 검색되도록. 크기의 12.5%(256 중 32)를 썼다. 겹침 크기 자체는 비교하지 않았다(한계).
5. → **문맥 손실은?** → 섹션/개요 보강. Contextual Retrieval, late chunking과의 차이. 5.2절.
6. → **semantic chunking은 왜 안 했나?** → 비용 대비 이득이 일관되지 않다는 연구 [R11, R13] + 제목 기준 분할도 이득이 없었던 내 실측.
7. → **청크 단위 vs 문서 단위 검색 결과는?** → 벡터는 청크로 찾고 문서로 합친다. 키워드는 문서 단위. 단위 불일치가 리랭커 실패의 원인이었다.

### 9.4 평가·운영 줄기

1. **검색 품질을 어떻게 쟀나?** → 42개 질의, 6개 유형, Recall@k, MRR, 짝지은 부트스트랩 CI. 6절.
2. → **42개로 충분한가?** → 아니다. 그래서 유의하지 않은 차이는 "유지"로만 말한다.
3. → **리랭커를 왜 뺐나?** → 4.3절. 일반론과 반대인 이유까지.
4. → **생성 품질은?** → 아직 안 쟀다. faithfulness를 다음 단계로. [R24]
5. → **긴 컨텍스트 모델이면 RAG가 필요 없지 않나?** → 비용·지연, Lost in the Middle, 둘을 같이 쓸 때 가장 좋다는 연구. [R18, R19]
6. → **에이전트가 grep으로 찾으면 되지 않나?** → 그것도 검색이다(just-in-time retrieval). 정확 일치에 강하지만 탐색이 느리고 의미 검색이 안 된다. 미리 만든 색인과 섞는 하이브리드가 실무 방향. [R20]
